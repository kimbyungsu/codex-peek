# 확인 대기 독립화·순차 검증 설계

> 2026-07-25 사용자 지적과 1차 Codex 검증을 반영한 구현 계약이다. Project MAP의 구조·patch 의미,
> 검증 세션 선택, 검증 상한 저장 형식은 바꾸지 않는다.

## 1. Project MAP 확인 대기 독립화

- bootstrap이 만든 `project-map/topology.json` 초안은 의미 판정과 독립적으로 유지한다.
- 의미 보강 결과 중 검증 담당이 필요한 항목이 `no-verifier` 또는 `inconclusive`가 되더라도 작업 묶음
  전체를 멈추지 않는다. 해당 patch는 적용하지 않은 `classified/verifier-resolved` pending으로 보존하고,
  브릿지 로컬 `enrich-deferred-v1` 장부를 먼저 내구 기록한 뒤에만 item cursor를 전진시킨다.
- 순서는 `propose/classify → deferred 기록·재판독 → cursor 전진`이다. deferred 기록 실패 때는 전진하지 않는다.
- deferred는 `mapId+patchId+opHash`, 원 job/item, **불변 실행 세대 `jobRunId`**, 판정 사유, 재시도 세대,
  호출 상태와 과거 결과를 보존한다. 새 의미 보강 job이 생겨도 이 장부는 교체되지 않는다. 대시보드의
  현재 적용·확인 대기·기각·조사 수는 `jobRunId`가 정확히 같은 기록만 합산하고, 같은 지도에 남은 다른
  실행 세대의 활성 기록은 `이전 실행 확인 대기`로 분리한다. `jobRunId`가 없던 구형 기록은 현재 실행에
  추측 귀속하지 않고 `구형 기록 귀속 확인 필요`로 표시한다.
- 일반 관측 tick과 화면 렌더는 deferred 검증 모델을 호출하지 않는다.
  - `no-verifier`: 새 검증 연결 세대당 한 번 또는 사용자 명시 재시도 때만 호출한다.
  - `inconclusive`·`uncertain-call`: 사용자 명시 재시도 때만 새 세대를 열어 호출한다.
  - 호출 전 `calling`을 기록한다. 결과 기록 전 프로세스가 죽으면 다음 실행은 `uncertain-call`로 바꾸고
    자동 재호출하지 않는다.
  - `support/reject`를 받은 뒤 적용·폐기 단계의 일시 오류는 저장된 판정을 재사용하며 검증 모델을 다시
    부르지 않는다.
- 이전 버전에서 남은 재분류 유물도 같은 deferred 장부로 이관한다. 유물만 일반 tick마다 검증을 재호출하는
  예외를 두지 않는다.
- 지원 판정은 pending 적용이 내구 종결된 뒤, 반박 판정은 pending 폐기가 내구 종결된 뒤 deferred를 닫는다.
  이미 종결된 pending은 결과를 대조해 멱등 종결한다. 기준선이 바뀌면 구 판정을 신본에 재사용하지 않는다.
- 닫힌 deferred에는 실제 종결 결과(`applied`·`rejected`)를 60일 동안 남긴다. 대시보드는 원 작업의 patchId와
  중복을 제거해 이 결과까지 합산한다. P2 적용·폐기 직후 프로세스가 종료되어도 다음 실행이 pending의 종결
  상태를 판독해 결과를 보충한 다음 deferred를 닫는다.
- 화면은 `적용`·`확인 대기`·`기각`·`조사 대기`를 분리한다. 기존 `skipped`는 호환용 합계로 남기되
  화면 판단에 쓰지 않는다. 확인 대기 장부 손상도 완료처럼 축소하지 않고 별도 복구 필요 상태로 표시한다.

## 2. 검증 왕복 안내와 실제 상한

- queued/running 검증 job은 **동시에 최대 하나**다. terminal 결과를 회수한 뒤에는 같은 사용자 턴에서
  다음 job을 순차 시작할 수 있다.
- 실패 또는 수용한 수정이 남으면 수정 후 다음 회차를 시작한다. 최종 상태가 통과하면 종료한다.
  유한 상한 `M/M`에서 통과하지 못하면 새 job을 만들지 않고 마지막 지적만 네 갈래로 마감한다.
- 권위 있는 `N/M`은 `ask-start` 시점이 아니라 child가 모델을 호출하기 직전 예약에 성공하고 job 영수증에
  기록된 뒤 생긴다. 예약 위치는 옮기지 않는다. 모든 유한·정상 집계 회차의 `ask-wait` 최종 출력에
  실제 `N/M`을 표시한다. 무제한은 숫자를 만들지 않고, 미집계는 N/M 권위가 없다고 표시한다.
- Stop의 3회 안전장치는 검증 왕복 수가 아니다. 같은 진행 상태에서 종료만 반복할 때의 재촉 횟수다.
  실제 캠페인 count, 최종 job/영수증, proof, 검증 이후 실제 수정 신호 중 하나가 바뀌면 진행 세대가
  바뀌고 재촉 횟수는 0부터 다시 센다. 이 내부 횟수를 사용자에게 `N/M`처럼 표시하지 않는다.
- `M/M`에서는 검증 호출만 끝난다. 구현 담당은 `[검증 상한 인계]` 아래에 수용·처리, 반박·종결,
  보관함 이관, 사용자 판단 필요, 경고등 의미, 권장을 모두 채우고 마지막 회차의 각 지적을 앞 네 절 중
  정확히 한 곳에만 둔다. 각 항목은 키로 시작하는 한 줄이며, 수용은 변경·확인 결과와 식별 가능한 파일·설정·시험·측정 근거, 반박은 관측·이유와 같은 근거,
  보관함은 같은 지적 제목의 실제 열린 영수증이 필요하다. 장부 손상·다른 항목 영수증은 종결로 인정하지 않는다. 사용자 판단 절이 비었으면
  질문 없이 `자동 정리 완료(통과 아님)`, 실제 선택이 있으면 한 묶음으로 `사용자 판단 대기`다. 마감문이
  실제 대화에 없으면 같은 안내를 최대 3회 한 뒤 `검증 상한 마감 누락` 빨강을 남기며, 나중에 작성되면
  자동 해소한다. 정상 상한 도달 자체를 `검증 미완`으로 기록하지 않는다.

## 3. 필수 반례

1. 첫 항목 검증 미연결·둘째 항목 독립 자동 적용 → 둘째 적용, 첫째 pending+deferred, job done.
2. inconclusive 뒤 tick·재시작 → 추가 모델 호출 0, 확인 대기 유지.
3. deferred 기록 직후 사망 → 재개 시 모델 재호출 없이 cursor 전진.
4. 명시 재시도 → 세대 1회 증가, 과거 inconclusive 미재사용, 새 호출 정확히 1회.
5. 새 검증 연결 → no-verifier만 새 연결 세대당 1회; inconclusive는 자동 호출 0.
6. support 뒤 일시 적용 실패 → 같은 support 재사용, 모델 호출 0.
7. CL-C/C-C 모두 `동시에 하나`와 순차 후속 행동을 같은 의미로 안내.
8. 1/5 실패→수정→2/5 허용, 2/5 통과→종료, 5/5 실패→6번째 호출 0.
9. 같은 진행에서 Stop 반복은 3회로 유한하지만, 새 검증 회수나 실제 수정 뒤에는 다시 차단한다.
10. 설치본 브릿지에서도 같은 상태기계와 한·영 문구를 사용한다.
11. 지연 support/reject와 P2 종결 직후 종료·재개 → 적용/기각 수가 각각 정확히 1이고 조사 필요로 빠지지 않는다.
12. 같은 jobKey의 실행 A 뒤 소스 세대 B가 생김 → A의 terminal·active 결과가 B의 네 수치에 섞이지 않고,
    A의 활성 기록만 이전 실행 확인 대기로 분리된다.
13. CL-C/C-C 모두 5/5 뒤 마감문 없음→정확한 단일 양식 요구, 사용자 선택 있음→`사용자 판단 대기`, 없음→`자동 정리 완료(통과 아님)`.
14. 마감문 없이 Stop 4회→`검증 상한 마감 누락`만 기록(`검증 미완` 오분류 0), 이후 마감문 작성→자동 해소.
15. 4회차에서 고친 지적과 5회차 현재 지적이 다름→5회차만 분류하며 과거 지적 부활 0.
16. 같은 지적을 두 갈래에 넣거나 반박 근거·보관함 영수증이 없음→마감 거부.
