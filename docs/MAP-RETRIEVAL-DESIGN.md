# 요청 기준 지도 검색(retrieval) 설계 — 초안 v1

## 왜 이걸 하나

검증자에게 매 회차 보내는 지도 조각이 **이번 요청과 무관하게** 골라진다.

- `withContract(prompt, ...)`는 요청문을 손에 쥐고 있으면서 `mapAttachSurface(ws, c, lang)`으로 부른다 —
  **요청문을 넘기지 않는다**([codex-bridge.js:70·92·169](../bridge/codex-bridge.js)).
- 실제 선택 기준은 하나뿐이다: **git이 알려주는 '지금 바뀐 파일'과 경로가 완전히 같은가**
  ([map-reader.js:256~](../bridge/map-reader.js)). 그다음 저장 순서대로 8개에서 자른다.
- 변경이 0건이면 정렬이 무의미해져 **원순서 앞 8개**가 실린다.

즉 *"설치 안내 문구를 고쳐줘"* 라고 해도 시스템은 그 말을 **읽지 않는다**. 이미 손댄 파일만 본다.

상한(노드 8·경로 200·설명 120)은 이 문제의 **증상 관리**였다. 잘 고르면 상한 값은 부차적이 되고,
못 고르면 상한을 올려도 관련 없는 것이 더 많이 실릴 뿐이다.

## 지켜야 하는 철학

이 제품은 **자동이 근간**이고 사용자는 철학·방향을 잡는다. 배선도 FAQ가 규정한다 —
*"적재·승격·강등은 전부 자동입니다. 직접 확인·정정, 확정 교범 내보내기, 고정·차단만 예외적인
선택 개입이고 안 써도 아무것도 멈추지 않습니다."*([extension.ts:1723](../src/extension.ts))

따라서 이 설계는 **사람에게 판단을 넘기는 방식으로 안전을 사지 않는다.** 검증에서 확정된 경계:

| 자동 | 사람(필수) | 사람(선택) |
|---|---|---|
| 옛 사건 격리·재입증, 출처 결속 신규 제안, 승격·강등, 로컬 순위화, 계측, 안전 기본값 | 새 외부 전송·유료 사용의 **지속 권한**, 제품 보증 경계 **승인**, 증거로 못 정하는 **의도·정책 선택** | 확인·정정·고정·차단·도장 — **안 해도 안 멈춤** |

## 핵심 결정: 검색 씨앗을 새로 밖에 내보내지 않는다

요청문을 정찰(외부 모델)에 넘기는 안은 **접는다.** 승인된 정책의 `ab-7`(비밀값·개인정보 유출)에 걸리고,
현재 동의 문구에 요청문 전송 항목이 없다([PRIVACY.md](../PRIVACY.md)).

⚠ **"요청문이 이 컴퓨터 밖으로 안 나간다"는 틀린 말이다.** `withContract`는 지금도 마지막에
**요청문 전체를 붙여 Codex 검증으로 보낸다**([codex-bridge.js:122](../bridge/codex-bridge.js)).
PRIVACY도 검증 본문이 전달된다고 밝힌다([PRIVACY.md:105](../PRIVACY.md)).

정확한 계약은 이것이다.

> **retrieval이 추출한 씨앗을, 기존 검증 전송 외의 어떤 곳으로도 새로 복제하지 않는다.**

금지 대상(sink)을 못박는다 — 씨앗 원문·검색어·매칭 사유를 **정찰 provider · MAP 문안 · 장부 사건 ·
carrier · note · 노출 사건 · stdout · stderr · 진단·통계 · 예외 문자열 · 캐시·임시파일**
어디에도 넣지 않는다.

⚠ *"외부로 나가는 것은 선택된 경로 목록뿐"*도 부정확하다. 기존 검증 프롬프트에는 경로 외에
**note · edge 줄 · 결합 후보 원문 · 관찰 신호**도 이미 실린다. 정확히는 이렇다.

> **기존 동봉 표면은 그대로이고, retrieval이 거기에 씨앗 필드를 추가하지 않는다.**

새 수신자도, 새 데이터 종류도 없으므로 **추가 동의가 필요 없다**.

### 검색 상한 (없으면 매 검증이 느려진다)

씨앗 검색은 **매 ask마다** 돈다. 상한 없이 저장소 전체를 뒤지면 대형 저장소에서 검증 시작이 밀리고,
사용자에게는 '멈춘 것'으로 보인다. `sliceTopology`가 노드·엣지·문자 상한을 함께 두는 것과 같은 이유다.

- 씨앗 개수 상한 · 검색 대상 파일 수 상한 · 읽는 바이트 상한 · 결과 개수 상한 · **시간 상한**
- 민감 경로는 검색 대상에서 제외(기존 `isSensitivePath` 재사용)
- 상한에 걸리면 **조용히 자르지 않고** 잘렸다고 남긴다(계측에서 `unknown` 처리)

### 씨앗 추출은 '의미'가 아니라 '글자'다 (정직 표기)

결정론으로 뽑을 수 있는 것은 **경로·코드 토큰·식별자·따옴표 인용문**이다. 이것은 **글자 기반 검색**이지
의미 유사도가 아니다. 문서에서 "요청 의도"라고 부르되 실체는 이 수준임을 명시한다.
추출 규칙·불용어·검색 대상·점수·상한을 구현 시 함께 문서화한다.

## 설계

### 1단계 — 출처 결속 (자동)

새로 쌓는 장부 사건에 출처를 적는다. 지금은 `sig`와 `type`만 필수라
([contract-lib.js:2590](../bridge/contract-lib.js)) "이게 어느 저장소 것인지" 증명할 방법이 없다.

**사건 종류마다 요구가 다르다.** 모든 사건에 같은 필드를 요구하면 근거 파일이 없는 사건
(`attached`·별칭·사용자 정정)의 `evidenceFp`가 무의미해진다.

| 사건 종류 | 필수 |
|---|---|
| **제안**(관계 주장) | `eventId` · `originRepoKey` · `basis` · `evidenceFp` + evidence 본문 |
| **파생**(동봉·확인·반박) | 자기 `eventId` + `originRepoKey` + `subjectEventId`(무엇에 대한 파생인지) |
| 사용자 정정·별칭 | 자기 `eventId` + `originRepoKey` + `subjectEventId` — 근거 지문 요구 없음 |

**왜 넷 다 필요한가**: 번호만으로는 소유권도 신선도도 증명되지 않는다(검증 지적).

**`originRepoKey`는 종류를 가리지 않고 중앙에서 붙인다.** 지금 `appendLedgerEvent`는 호출자가 준 `ws`로
파일만 고르고 사건 내용은 그대로 적는다([contract-lib.js:2590](../bridge/contract-lib.js)).
확인 생산자도 대상과 사건을 따로 넘긴다([codex-bridge.js:990](../bridge/codex-bridge.js)).
파생 사건에 출처가 없으면 같은 구멍이 남는다.

그리고 파생 사건은 기록 직전에 **두 가지를 확인한다**.

- `subjectEventId`가 **같은 대상 장부에 실재**하는가
- subject의 출처가 **현재 대상과 같은가** — 다르면 **기록 거부**

#### 압축이 증명 사슬을 끊지 않게 (검증 blocker · `ab-5`)

장부는 12,000건을 넘으면 약 10,000건으로 줄인다([contract-lib.js:2588·2602](../bridge/contract-lib.js)).
그런데 보존 우선순위와 역순 최신 선택은 **`sig`와 상태 기준**이라
**`eventId` 참조 도달성을 지키지 않는다**([2664·2668](../bridge/contract-lib.js)).

그러면 이런 일이 난다 — 오래된 제안 P와 그걸 가리키는 확인 C가 있을 때, **압축이 P만 지우고 C를 남긴다.**
그 뒤로는 둘 다 나쁘다.

- 읽을 때 subject 실재를 검사하면 → **멀쩡한 확인 C가 고아가 되어 승격 증명이 사라진다**
- 검사를 건너뛰고 `sig`만 믿으면 → **방금 만든 출처 결속 계약이 무력화된다**

**되돌릴 수 없는 기록 파괴**라 `ab-5`에 해당한다. 계약을 하나 더 둔다.

> **압축은 남기기로 한 파생 사건의 subject 사슬을 함께 남긴다.**
> 압축 레코드를 만들 때는 **같은 안정 subject id와 출처를 물려받는다.**

**12,000건 초과 반례**가 필요하다 — 압축을 실제로 돌려 P가 지워지고 C만 남는 상태가 생기지 않는지.

**단, 사슬 보존만 요구하면 압축이 무력화된다(검증 [주의]).** 파생이 파생을 가리키는 것을 허용하면
보존해야 할 집합이 입력 전체까지 커진다. 압축기는 **결과가 줄어들 때만 다시 쓰므로**
([contract-lib.js:2675](../bridge/contract-lib.js)) 아무것도 안 줄면 **다음 append마다 전량을 다시
읽고 계산한다**([2601·2678](../bridge/contract-lib.js)) — 장기 프로젝트에서 기록이 느려지고
사용자에게는 '멈춘 것'으로 보인다.

**사슬 길이 상한으로 자르면 안 된다** — 그건 다시 `ab-5`(증명 파괴)다. 대신 **구조로 제한한다**.

- 모든 파생 사건은 **다른 파생이 아니라 안정된 루트 제안을 직접 가리킨다**(사슬이 1단계로 고정)
- 압축은 **루트별 현재 상태를 정본 스냅샷 하나로** 만들고 같은 root id·출처를 물려받는다
- 반례는 고아 부재뿐 아니라 **압축 후 크기가 실제로 줄었는지**와 **반복 append 시 재압축이 억제되는지**도 본다

**대상이 정당하게 바뀐 경우**는 이 검사로 풀지 않는다. 장부 키는 경로 기반이라
([contract-lib.js:1993](../bridge/contract-lib.js)) 이동·대상 변경 뒤에는 **기존 사건을 격리하고
현재 대상에서 재입증해 새 제안을 만드는** 2단계 경로가 맞다.

**생산자가 여럿이다.** `appendLedgerEvent`를 부르는 곳은 문서에 적은 파일보다 많다 —
정찰 제안([scout-providers.js:255](../scripts/scout-providers.js)), 선택 개입
([extension.ts:4013](../src/extension.ts)), backfill·note·reconcile·migrate가 각각 직접 부른다.
**중앙에서 채울 필드와 호출자가 줘야 할 필드를 먼저 가른다** — 안 가르면 일부 생산자만 출처를 남기고
나머지는 빈 채로 쌓여 다시 추정에 의존하게 된다.

### 2단계 — 옛 사건 자동 재입증 (자동 · 사람 개입 0)

옛 작업공간 키 장부는 **격리 상태로 둔다.** 그리고 **현재 코드에서 관계를 다시 입증**한다.

```
옛 사건 → 경로 추출 → 격리 저장소에 보관
        → 현재 대상에서 그 관계가 실제로 성립하는지 재입증
        → 성공 시에만: 현재 출처가 박힌 '새 제안' 생성
        → 실패·판정 불가: 격리 유지(삭제하지 않음)
```

**옛 확인·반박·동봉 횟수는 복사하지 않는다.** 새 제안은 신분 0에서 시작해
기존 승격 규칙(강한 확인 1회 / 서로 다른 검증의 공동 인용 2회)을 그대로 통과해야 한다.

#### 재입증 계약 (이게 없으면 '성공 판정'이 결국 경로 실존과 같아진다)

옛 사건의 자유 문장을 **허용 목록의 typed claim으로 변환**한 뒤에만 판정한다. 변환 못 하면 격리 유지.

| 항목 | 규약 |
|---|---|
| 참조 방식 | 옛 사건은 원래 장부에 두고 `legacyEventHash`로만 가리킨다(복사·이동 금지) |
| claim 형태 | 관계 종류 · 양 끝 경로와 심볼 · 방향 — 이 셋이 다 나와야 한다 |
| 근거 필수 | `evidence: [{file, locator, quote, contentHash}]` — 현재 대상에서 실제로 읽은 것 |
| 기계 검증 관계 | import·호출·정규식 소비처럼 파서로 대조 가능한 것은 **직접 대조**한다 |
| 의미 관계 | 정찰 역할의 typed 결과로 **제안만** 한다. 승격 검증과 **같은 실행 결과를 재사용하지 않는다** |
| 기록 직전 | target identity · basis · 모든 contentHash를 **다시 대조**한다 |
| 실패 처리 | 불일치·미지원 관계·불확실 = **격리 유지**(삭제도 승격도 하지 않음) |

이 수준은 새로 만드는 게 아니다 — P8 보강이 이미 evidence quote·contentHash·현재 지문 재검사를
계약으로 쓴다([MAP-V2-DESIGN.md 661·668](MAP-V2-DESIGN.md)). 같은 계약을 여기에 적용하면
**사람 개입 없이** 오귀속을 닫을 수 있다.

**하지 말아야 할 것(검증 blocker)**: *"경로가 전부 실존하면 참고 등급으로 편입"*은 안 된다.
참고 등급도 다음 정찰 자료에 실리고([out/ledger-events.js:358](../out/ledger-events.js)),
미검증 결합은 오히려 검증 동봉 후보로 **먼저** 뽑힌다([contract-lib.js:2956](../bridge/contract-lib.js)).
게다가 `src/extension.ts` 같은 경로는 **어느 프로젝트에나 있어** 실존이 소유 증거가 못 된다.
실측: 옛 31사건 중 전 경로 실존 13건(42%) — 그 42%가 이 저장소 것이라는 뜻이 아니다.

### 3단계 — 요청 기준 로컬 순위화 (자동)

`withContract`가 이미 가진 요청문을 지도 선택까지 전달하고, **네 신호를 합쳐 순위를 매긴다.**

| 신호 | 출처 | 지금 있나 |
|---|---|---|
| ① 요청 의도 | 요청문에서 뽑은 씨앗을 **로컬 검색** | **없음** |
| ② 변경 파일 | `git status` | 있음(유일) |
| ③ 관찰 일지 | 확인·참고 등급 항목 | 있으나 선택에 미사용 |
| ④ 구조 이웃 | ①②③에서 지도로 한 칸 확장 | 부분(enrich에 선례) |

**몫은 고정하지 않는다.** 축별 최소 몫을 예약하되 **후보가 모자란 축의 몫은 남는 축에 재배분**한다
(검증 권고 — 고정 몫은 작은 프로젝트에서 빈자리를 만든다).

**④가 핵심이다.** 요청문 유사도만으로 고르면 지도의 존재 이유를 잃는다 — 지도의 값은
*요청에 안 적힌 연결*을 찾아주는 데 있다. 실제 사례: 요청은 "설치 안내 문구"였고 실제 결함은
설정 읽기·백업·화면 표시에서 나왔다. 그 단어들은 요청문에 없다.
`enrich-providers.js`의 **씨앗 → 인접 → 잔여** 순서가 이미 같은 형태다 — 새로 발명하지 않는다.

**상한은 유지한다.** 잘 골라도 관련 노드가 8개를 넘을 수 있고, 상한은 관련성과 별개로
크기를 묶는 역할이다(검증 지적 — 내가 "상한은 부차적"이라 한 것은 틀렸다).

### 4단계 — 계측 (자동 · 연결은 하지 않음)

지금은 무엇이 검증자에게 **노출됐는지**를 사건으로 남기지 않는다. `attached`는 다른 뜻이다 —
**정찰 자료에 실렸다**는 뜻이지 검증자에게 동봉됐다는 뜻이 아니다
([scope-package.js:17](../scripts/scope-package.js)).

회차별 **노출 스냅샷**을 남긴다. `mapItems`에는 지금 id가 없고 `{path,note}`뿐이라
([map-reader.js:326](../bridge/map-reader.js)) 나중에 후보별 경로를 복원할 수 없다. 그래서 이만큼 남긴다.

`targetIdentity`(저장소 정체성 — 경로 해시 아님·명세 §2와 같은 축) · `askId` · 지도 세대 지문 · retrieval 버전 · **후보별 {종류, id, 축, 정규화 경로 집합}**

**종류를 나눠 담는다.** 실제 프롬프트 텍스트에는 node뿐 아니라 **edge · 결합 후보 · 관찰 신호**도
실리는데([map-reader.js:325](../bridge/map-reader.js)) 구조화 반환은 `mapItems`와 `couplings`뿐이다
([map-reader.js:326](../bridge/map-reader.js) · [codex-bridge.js:95](../bridge/codex-bridge.js)).

**그런데 종류를 나누는 것만으로는 지표 분모가 안 정해진다.**

- **관찰 신호**에는 인용할 경로가 아예 없다
- **edge 줄**에는 양 끝 이름만 나오고 **뒷받침 경로는 출력되지 않는다**

이걸 경로 인용률 분모에 넣으면 **항상 미인용**으로 잡히고, 반대로 뒷받침 경로를 넣으면
**보여주지도 않은 경로를 노출된 것으로 오인**한다. 그래서 두 집합을 **가른다**.

| 집합 | 무엇 | 쓰임 |
|---|---|---|
| **노출 감사 집합** | 프롬프트에 실린 것 전부(종류 포함) | 무엇을 보냈는지 남기는 기록 |
| **지표 적격 집합** | 그중 **실제로 렌더링된 경로**를 가진 것만 | 인용률 계산의 분모 |

후보마다 `metricEligible`과 **'실제로 렌더링된 경로 집합'**을 함께 적는다. 분모는 적격 집합만 쓴다.

그리고 두 값을 계산한다. **기존 함수를 재사용한다** —
`citedResolvedPaths`([codex-bridge.js:400](../bridge/codex-bridge.js))로 실존·유효 라인 인용을 뽑고,
'실제로 읽은 근거'만 세려면 `citedFilesUnseenExact`([codex-bridge.js:809](../bridge/codex-bridge.js))
결과를 함께 결속한다.

- **인용률** — 노출한 것 중 검증이 실제로 인용한 비율
- **동봉 밖 인용률** — 검증이 인용했는데 노출 목록에 없던 것의 비율

⚠ 두 번째 이름을 **'발견률'이 아니라 '인용률'**로 쓴다. 목록 밖 인용이 곧 '놓친 발견'은 아니다.
진짜 발견률은 findings와 연결해야 나오므로 그건 나중 항목이다.

계측 실패는 **낮은 점수가 아니라 `unknown`**으로 남긴다.

**이 단계에서 자동 재정찰과 연결하지 않는다.** 연결하면 이런 고리가 생긴다 —
*인용률 낮음 → 재정찰 → 후보 증가 → 분모 커짐 → 인용률 더 낮음 → 재정찰*. 자기증폭이다.

### 5단계 — 자동 재정찰 (나중 · 억제 조건 선행)

표본이 쌓이고 억제 조건이 갖춰진 뒤에만 연결한다. 필요한 억제:
같은 근거 지문당 1회 · 단일 실행 · 최소 표본 · 연속 실패 횟수 · 냉각 시간 · 회차·시간 상한 ·
개선 없으면 종결 · **유료 담당으로 자동 승격 금지**.

## 검증

- `npm test` 전체 체인 EXIT=0
- **오귀속 차단 반례**: 두 임시 저장소가 같은 상대경로를 갖게 만들고, A에서 쌓인 옛 사건이
  B의 정찰 자료·검증 동봉 어디에도 실리지 않는지. 재입증에 성공한 것만 **새 출처로** 들어오는지
- **요청 축 반례**: 변경 0건 상태에서 요청문만 주고 선택 결과가 달라지는지(지금은 원순서 앞 8개)
- **구조 이웃 반례**: 요청문에 없는 단어의 파일이 이웃 확장으로 뽑히는지
- **몫 재배분 반례**: 한 축의 후보가 0건일 때 그 자리가 비지 않는지
- **계측 반례**: `attached`와 새 노출 사건이 섞이지 않는지, 계측 실패가 `unknown`으로 남는지
- **씨앗 sink 반례**: 씨앗 원문·검색어·매칭 사유가 **정찰 꾸러미 · DeepSeek 본문 · MAP 문안 ·
  장부 사건 · carrier · note · 노출 사건 · stdout · stderr · 진단·통계 · 예외 문자열 · 캐시·임시파일**
  어디에도 안 실리는지(요청문 자체는 지금도 검증에 가므로 그건 대상 아님)
- **압축 보존 반례**: 12,000건을 넘겨 압축을 실제로 돌렸을 때 ⓐ남은 파생 사건의 subject가 함께 남는지
  (P만 지워지고 C가 고아가 되지 않는지) ⓑ**압축 후 크기가 실제로 줄었는지**
  ⓒ**반복 append에서 전량 재압축이 억제되는지** ⓓ압축 전후 `deriveLedger` 결과가 같고 이후 임의의
  정상 사건을 덧붙여도 상태 전이가 같은지
- **지표 적격 반례**: 경로 없는 관찰 신호와 뒷받침 경로가 안 보이는 edge가 분모에서 빠지는지
- **검색 상한 반례**: 파일·바이트·시간 상한에 걸리면 잘렸다고 남기고 `unknown`이 되는지
- **provenance 반례**: 사건 종류별로 요구 필드가 다르게 강제되는지, 모든 생산자가 출처를 남기는지
- 단계마다 Codex 검증 1회, 수정 후 설치본 갱신

## 구현 전 반드시 확정할 것

설계는 여기까지고, 아래 다섯은 **코드를 쓰기 전에** 값·규칙까지 정해야 한다(검증 요구).

1. **재입증 typed 계약** — 허용 관계 종류 목록, 각 종류의 판정 방법, evidence 형식
2. **사건 종류별 provenance 스키마** — 중앙이 채울 필드 vs 호출자가 줄 필드
3. **씨앗 추출·검색 규칙과 상한** — 추출 대상, 불용어, 검색 범위, 점수, 다섯 상한값, sink 금지 목록
4. **노출 스냅샷 형식과 지표 정의** — 후보별 필드, `metricEligible` 판정 규칙, 두 지표의 계산식,
   `unknown` 판정 조건
5. **압축의 참조 보존 계약** — 파생이 루트를 직접 가리키게 하는 구조, 루트별 정본 스냅샷 방식,
   압축 후 크기 감소와 재압축 억제 확인 방법. 여기에 아래 둘을 반드시 함께 정한다(검증 [주의] 2건).

   **⒜ 루트가 너무 많아 못 줄이는 경우** — 깊이를 1단계로 고정해도 **고유 루트 수 자체가 상한을 넘으면**
   스냅샷도 그만큼이라 결과가 안 줄고, 그러면 다음 append마다 전량을 다시 계산한다. 둘 중 하나를 택한다.
   - 압축 불가 루트를 **별도 보존 계층으로 옮기고** 활성 장부에는 정본 스냅샷만 둔다
   - 상한 초과를 허용하되 **'이번 세대는 더 못 줄임' 표식**을 남겨 다음 append의 전량 재시도를 막는다

   **⒝ 스냅샷이 승격·복권 증명을 보존하는 방식** — 기존 규칙은 단순 횟수가 아니라 `grade`·`cited`·
   `seen`·`echoed`와 **서로 다른 `askId`**를 본다([ledger-events.ts:104·136](../src/ledger-events.ts)).
   복권은 **마지막 유효 반박 이후의 확인만** 다시 센다([214·233](../src/ledger-events.ts)).
   상태와 총횟수만 남기면 '서로 다른 검증 2회였는지', '반박 전 확인인지'를 알 수 없어
   **잘못 승격하거나 정당한 복권을 잃는다.**

   스냅샷 계약은 **동치 조건**으로 정의한다.
   > 압축 전후 `deriveLedger` 결과가 같고, 이후 **어떤 정상 사건을 덧붙여도 상태 전이가 같다.**

   그러려면 최소한 이만큼을 보존한다 — 등급별 임계까지의 **서로 다른 `askId`** · **마지막 유효 반박 경계** ·
   **반박 이후 확인** · **사람 확인** · **차단·고정·별칭 순계**.

⚠ **코드 구현은 위 다섯이 확정되기 전에 시작하지 않는다.** 설계 구체화까지가 지금 할 수 있는 일이다.

## 남는 한계 (정직)

- 옛 사건 재입증은 **관계가 지금도 성립할 때만** 살아난다. 이미 사라진 관계는 복원되지 않는다 — 의도한 것이다.
- 요청문이 모호하면(`이어서`, `고쳐줘`) ① 축은 빈다. 그때는 ②③④로 떨어진다 — 지금과 같은 수준.
- 지도가 폴더 단위인 동안에는 ④의 이웃 확장이 폴더 단위로만 넓어진다. 밀도 개선은 별건이다.
- 계측이 쌓이기 전에는 이 설계가 실제로 나아졌는지 **모른다**. 4단계가 그 답을 만든다.
