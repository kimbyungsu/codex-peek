### 1-A. 발췌가 지금 어떻게 만들어지고 어떻게 검사되나

- 선정: `bridge/enrich-providers.js:76-99 excerptSelectionFor(topo, changed)` — 지도 조각(변경 파일 앵커 노드 우선)과 **변경 파일 목록**에서, 민감 경로·200자 초과 경로를 뺀 뒤 **최대 20개**(`FILES_MAX`, :36) 순서대로. 프롬프트 조립(`buildEnrichPrompt` :110-155)과 발동 관문(`answerableInput`, map-enrich.js 1702)이 **같은 함수**를 쓴다(단일 경로 계약 — 2026-08-04 봉합).
- 본문: `excerptBodyFor(repo, f)` :105-108 — 파일 **앞에서 4,000자**(`FILE_EXCERPT_MAX`, :35). 바뀐 위치와 무관하다.
- 출력 계약 문구는 "quote는 위 발췌에 실제로 존재하는 원문 그대로"(:138)지만, 실제 검사(`map-enrich.js` runAttempt 1760-1772)는 **파일 전체** `body.includes(quote)` 다. 발췌 결속은 add_node 의 앵커 파일이 발췌에 실렸는지만 본다(validateEnrichResult). 불일치 진단 `evidenceMismatchDetail`(2054-2068)만 `inExcerpt`(앞 4,000자 안인가)를 계산하되 **실패했을 때만** 기록한다 — 성공 항목의 인용 위치는 어디에도 남지 않는다.
- 실측(2026-09-19 진단 프롬프트): 92,945자 · 주석/빈 줄 28% · 발췌 20파일 중 인용 9 · 실제 실행은 5파일 규모.

### 1-B. 호출과 시도가 지금 어떻게 기록되나

- 시도(attempt)는 **호출 전에** 기록된다(map-enrich.js 1704-1710: `{attemptId, provider, consentGen, phase:"running", startedAt}`) — '불확실 호출' 감사 재료. 실패는 `failureStage(call|response|validation|conversion)`·`failureCode`·`failureFile`·`failureDetail`·`droppedItems`로 구조화된다(1727-1743·1778-1786·1795).
- 비용 장부(`recordCliUsage`, enrich-providers.js:22-24 → `CL.appendScoutUsage`, `stats/scout-usage.jsonl`; 행에 `flow:"map-enrich"`·`provider`·`callId`·`repoKey`·`runId`·`jobKey`·`jobRunId`·`charsIn/Out`)는 **'프로세스가 떴다'의 기록이지 '요금이 발생했다'의 권위가 아니다**: 기본·정밀은 자식 PID 만 생기면 종료 오류·빈 출력 판정 전에 기록하고(:174-175·:199-200), 경제형은 실패·중단을 포함해 finally 에서 기록하며(deepseek-bridge.js:108-122), 반대로 장부 잠금·쓰기 실패는 호출자가 무시한다(contract-lib.js:357-368). 과다·누락이 모두 가능하므로 호출 수의 **권위 출처는 작업 장부의 시도 결과**(아래)로 둔다.
- 시도 결과로 '답을 받은 호출'을 확정할 수 있다: 시도가 `applying`/`done`에 이르렀거나 실패 단계가 `response|validation|conversion`이면 담당의 답이 도착한 것이고, 실패 단계가 `call`이면 답 없이 끝난 것(요금 발생 여부는 불확실). 경제형 어댑터 안 형식 교정(deepseek-bridge.js:190-194)은 한 시도 안의 요청 2건이라 '시도 1'로 센다(안내 문구에 '경제형은 시도당 최대 2요청' 병기).
- 실행 단위 사건은 `map-automation-v1`(enrich-start·enrich-job-terminal·enrich-run-terminal, map-enrich.js 1088-1105)에 `trigger`(consent/retry/probe/tick/cli/link)·`reasonCode`·`provider`로 남는다.
- 자동 호출 규칙: 한 실행에서 라우터가 정한 담당 1회 + 자동형은 승격 1회(driveAttempts 1659-1690·map-router.js:16-46, 정밀 단독은 실패 시 즉시 보류) ; 답이 도착했는데 거부된 보류(response·validation·conversion)는 **딱 한 번** 스스로 다시 시도(1563-1587, `retryFrom`으로 한도 관리) ; 사용자 '다시 시도'는 무제한(retryFrom 재설정, extension.ts 753-757). 기본형(Claude, 무과금)은 이 분기 밖이다: 첫 거부는 `park(null, "self-failed")`(1682 — 작업 장부를 바꾸지 않아 작업이 open 으로 남음) → 다음 관측에서 ⑥ open → resumeJob 의 failed 분기(2290-2320)가 한 번 더 부르고, 그 답도 거부되면 `self-failed` 로 보류(2308·parkR)한다(화면·시험도 self-failed 를 사람 몫으로 분류 — extension.ts 639·tests/enrich-visibility.test.js 257). **소스가 그대로인 구간**에서 사람 없이 최대 = 기본형 2(재개 경로) · 정밀 2 · 경제 2 시도(각 시도 최대 2요청) · 자동형 4. 단 호출 중 편집이 반복되면 `source-changed` 보류가 다음 실행에서 retryFrom 을 옮겨 스스로 재개하므로(1542-1549·1678) 같은 작업의 호출은 그때마다 늘 수 있다 — **절대 상한이 아니다**(화면에 상한을 적지 않고 실제 횟수만 적는 이유).
- 재시도 이력의 출처(현재): `retryFrom` 이동은 다섯 곳이 같은 형태로 쓴다 — 문서·산출물뿐 보류 재개(1511)·준비 회복 재개(1530)·편집 중 충돌 재개(1544)·자동 재시도(1579)·사용자 '다시 시도'(extension.ts 755). 작업 장부만으로는 원인을 구별할 수 없고, 원인을 적는 경로 로그(`auto-retry/parked-once` 1582·appendRouteLog 1004-1009 는 실패를 삼킴)와 실행 사건(map-automation-v1 — append 결과 미확인 1098-1102·1341, 60일 뒤 정리 contract-lib.js:342-390)은 **best-effort** 라 누락 행과 실제 0회를 구별할 수 없다. 따라서 표시용 이력은 strict 작업 장부에 새로 남긴다(§3).
- 화면(extension.ts 2795-2835 → 7863-7867)은 시도의 마지막 실패·적용/기각/제외 건수만 싣고 **호출 수·재시도 이력**은 보여주지 않는다. 안내 패널(2197-2260)의 비용 문구는 준비 점검 기준("DeepSeek 최대 2회(형식 교정 1회 포함)·Codex 1회")이고 보강 실행의 호출 수는 적혀 있지 않다.
- 비용 장부 판독기는 이미 있다: `readScoutCosts`(extension.ts 1952-1959, `MAP_USAGE_FILE` :73)가 같은 파일을 28일 집계로 읽는다. 장부는 60일 보존(`trimScoutUsage`).

### 1-C. 되묻기가 지금 어디에 있고 없나

- 경제형: 어댑터 안에서 형태(shape) 실패 시 **원격 재호출 정확히 1회**("형식이 틀렸다…" 메시지+직전 답 동봉, deepseek-bridge.js:190-194). 실행기 시도로는 1회로 보인다.
- 정밀형·기본형: 어댑터 안 교정 없음. 유료 담당(정밀·경제·자동형)은 실행기 층의 **자동 재시도 1회**(AUTO_RETRY_REASONS 1571 — precision/economy/both-failed 만), 기본형은 **재개 경로의 재호출 1회**(1-B — 첫 거부 뒤 open 잔존 → 다음 관측 재개 → 두 번째 거부=self-failed 보류)로 서로 다른 경로를 타지만, 어느 경로든 재호출 프롬프트는 첫 호출과 **완전히 같다**(거부 이유를 넘기지 않음 — buildEnrichPrompt 입력에 직전 시도 정보 없음).
- 보관함 4b25e7cfa0555b7a 의 사고(2026-09-18, 항목 1개 evidence 누락으로 답 전체 schema-invalid)는 그 뒤의 **항목 단위 관문**(D-2026-09-18-enrich-item-gate·커밋 82365ba)으로 형태가 바뀌었다: 이제 그 항목만 `droppedItems`로 빠지고 나머지는 반영된다. 전부 제외됐을 때만 시도 실패다(1774).

## 2. 축 A — 발췌: 측정 → 읽기 강제 → 옵션

### 2-1. A-1 측정(관찰 전용 · 묶음 1) — "지금 보낸 발췌를 얼마나 읽고 인용하나"

- 실행기: 1단계 관문에서 **통과한 항목**의 인용(evidence·claims 의 quote)마다 '실제로 발송된 발췌 범위 안인가'를 판정해 시도에 요약을 남긴다: `attempt.citation = { total, inExcerpt, outside, filesCited, filesSent }`. 판정은 `evidenceMismatchDetail`의 `inExcerpt` 계산과 같은 정규화(CRLF·trim·공백)를 성공 경로에도 적용한다(함수 재사용 — 두 벌 금지). 발췌 범위는 프롬프트를 만든 그 선정 함수의 결과(파일·범위)를 그대로 쓴다.
- 장부: `ATTEMPT_KEYS`(map-enrich.js:156)에 `citation` 을 선택 필드로 추가하고 형태(정수 5개)를 strict 검사(236 부근)에 넣는다 — 옛 판독기 창은 이미 bridge-stale 배너가 재로드를 안내한다. 옛 기록(필드 없음)은 그대로 통과.
- 화면: 카드 한 줄 "인용 n건 · 그중 보낸 발췌 안 m건 · 인용된 파일 a/보낸 파일 b" (ko/en). 지도 통계 탭에는 넣지 않는다(카드 한 줄로 충분 — 통계는 묶음 3 뒤 필요 시).
- 용도: D3 프리셋 수치의 근거 · D1 전환 전 기준선(발췌 밖 인용 비율이 곧 "결속 시 잃는 항목 비율").

### 2-2. A-2 읽기 강제(묶음 2 — D1·D2 결정 후)

(a) **인용 결속** — 모든 항목의 quote 가 '보낸 발췌 범위 안'에 있어야 통과. 실패는 항목 단위 제외(`stage:"evidence"`, 새 코드 `evidence-outside-excerpt`, detail 에 파일·범위·quoteHead). 전부 제외면 종전대로 시도 실패 → 자동 재시도 1회 대상(response/validation) 유지. 출력 계약 문구(:138)와 검사가 비로소 일치한다.
(b) **바뀐 부분 주변 발췌** — 선정 함수가 파일별 '범위 목록'을 돌려주고 본문 판독기가 그 범위만 잘라 붙인다:
  - git 기준 큐: 소비 기준점(consumed baseline head)~HEAD 의 `git diff -U0`(hunk 헤더에서 줄 범위) + 작업 트리 변경(`git diff -U0` 대비 HEAD)의 합집합 → 각 hunk 앞뒤 N줄(구현자 제안 40줄, 프리셋의 파일당 글자 상한 안에서) 병합. git 명령은 기존 관례(`-c safe.directory=*`, 5초 제한)로 호출하고 실패·초과·신규 파일(hunk 전체)·이름 변경은 **앞부분 폴백**(현행 규칙) — 폴백은 침묵하지 않고 발췌 제목에 표기한다.
  - git 없는 큐(historyless): 파일 단위 변경만 알 수 있으므로 앞부분 폴백(현행).
  - 발췌 제목에 위치를 적는다: `### src/a.js (변경 주변 L120–180, L300–330)` / `(앞부분)` — 모델이 "이 파일의 어느 부분을 받았는지" 알고, 검증자(사람)도 화면에서 같은 표기를 본다.
  - 단일 경로 계약 유지: 발동 관문(`answerableInput`)·프롬프트·(a)의 결속 검사·A-1 측정이 **같은 선정 결과**를 쓴다. 편집 중 충돌(preSha 지문)은 그대로.
  - 프롬프트 지시문은 늘리지 않는다 — 범위 표기는 자료(제목)이지 규칙 문장이 아니다(HARNESS-STRUCTURE §B2(4) 관례).
(c) strict 장부 변경 목록(검토 1판 보완): 새 실패 코드 `evidence-outside-excerpt`는 `FAILURE_CODES`(map-enrich.js:159)에, 제외 항목 detail 의 새 종류(파일·범위·quoteHead)는 `validFailureDetail`(2036)과 droppedItems 정확 키 검사(252)에 추가한다. 화면의 failureText 는 닫힌 열거만 문구로 바꾸므로 새 코드의 ko/en 문구를 함께 넣는다. 옛 기록은 그대로 통과(추가만).
(d) 시험: 발췌 범위 밖 인용=항목 제외·범위 안=통과 · hunk 병합(겹침·인접·상한 절단) · git 실패/신규 파일 폴백·제목 표기 · 관문과 프롬프트의 선정 일치(기존 단일 경로 시험 확장) · 민감 경로는 hunk 여도 제외(ab-7).

## 3. 축 B — 호출 횟수 표시(묶음 1)

- 권위 출처(검토 1·2판 blocker 정정): **작업 장부(strict·잠금·fence 아래 기록)만** 표시의 권위다. 비용 장부(scout-usage)·경로 로그·실행 사건은 best-effort(실패 삼킴·60일 정리)라 감사용으로만 두고 화면 수치의 재료로 쓰지 않는다. 요금은 각 서비스 명세서가 권위 — 화면은 '요금'이라는 말을 쓰지 않는다.
- 장부 보강(작업 수준 선택 필드 1개): `job.resumes = [{ kind, at, fromAttempts }]` — `retryFrom` 을 옮기는 다섯 곳(1511·1530·1544·1579·extension.ts 755)이 **같은 fenced/locked 갱신 안에서** 한 항목을 덧붙인다. `kind` 는 닫힌 열거 `input-doc-only | not-ready | source-changed | auto-retry | manual`(`JOB_KEYS`(153)에 `resumes` 추가·strict 검사 232 부근: 배열·kind 열거·ISO 시각·정수·단조 증가; 옛 기록은 부재 허용). 사용자 '다시 시도'는 확장이 `updateEnrichJob` 으로 쓰므로 같은 규칙으로 덧붙인다(옛 판독기 창은 bridge-stale 배너가 재로드 안내). 삭제·덮어쓰기 없음(추가만 — ab-5).
- 순수 계산(새 파일 `bridge/enrich-calls.js`, 유지보수 방침 ①): `enrichCallSummary(job)` — 입력은 작업 장부 하나 →
  - `answered`: 담당별(claude/deepseek/codex) '답을 받은 시도' 수 = 시도가 applying/done 에 이르렀거나 실패 단계 ∈ {response, validation, conversion}. `callFailed`: 실패 단계 = call 인 시도 수(답 없음 · 요금 여부 불확실이라 '호출 실패'로만 표기). `uncertain`: 답 여부를 알 수 없는 시도 = phase running 으로 남은 것 **또는** 복구가 `parked/uncertain-call` 로 영속한 것(2263-2265 — 유료 호출 중 프로세스가 죽은 시도는 이 상태로 남는다; 뒤에 재시도해도 과거 시도는 배열에 남으므로 집계에서 사라지지 않는다). 경제형은 시도당 최대 2요청임을 문구로 병기.
  - `autoRetry`: 보류 중이면 실행기 규칙과 동형으로 "남음/사용됨/해당 없음"(parkedReason ∈ AUTO_RETRY_REASONS ∧ 마지막 실패 단계 ∈ {response,validation,conversion} ∧ retryFrom 유무 — extension.ts 634-669 의 동형 관례). 보류가 아니면 `resumes` 의 auto-retry 항목으로 "사용됨/미사용".
  - `userRetries` = `resumes` 의 manual 수 · `sourceChangedResumes` = source-changed 수(있으면 "편집 중 충돌로 다시 n회" 병기 — 호출이 늘어난 이유를 숨기지 않는다) · 그 외 kind 는 합쳐 "자동 재개 n회".
  - `resumes` 부재(옛 기록)는 0 이 아니라 `unknown`("이 작업은 이전 판에서 시작돼 재시도 이력이 없어요") — P10 화면 관례 "원장 판독 실패를 실제 0건과 구분".
- 화면: 자동 보강 상태 줄 아래 한 줄(ko/en) — "이번 작업: 답 받은 호출 3회(Codex 2 · DeepSeek 1) · 호출 실패 1회 · 자동 재시도 사용됨 · 사용자 재시도 1회 · 편집 중 충돌로 다시 1회". 안내 패널의 문구는 '상한'이 아니라 **규칙**으로 적는다("소스가 그대로면 사람 없이 정밀 2회·경제 2회(시도당 최대 2요청)·자동형 4회까지, 호출 중 편집이 있으면 그때마다 다시") — 숫자는 상수(라우터 표·자동 재시도 규칙·어댑터 교정 횟수)에서 계산해 넣는다(하드코딩 금지).
- 시험: 순수 함수 표(정밀 2회·자동형 승격·경제형 교정은 시도 1·call 단계 실패 분리·running 잔존과 parked/uncertain-call 모두 uncertain·기본형 재개 경로 2회·retryFrom 유무·resumes kind 별·resumes 부재=unknown) + 다섯 재개 경로 각각이 resumes 항목을 남기는 실행 시험(기존 [10] 입력 자기치유·자동 재시도·source-changed·수동 재시도 시험에 단언 추가) + strict 검사(이형 kind·비단조=damaged) + 화면 배선 소스 검사.
- 하지 않는 것: 비용 장부·경로 로그·실행 사건을 표시 재료로 쓰기 · 요금 표시 · 절대 상한 표시 · 통계 탭 확장(요청 시 별도).

| C | 정밀 전용 어댑터 안 교정 호출 1회(경제형 동형) | +1(정밀은 상태 없는 실행이라 프롬프트+직전 답+오류를 전문 재전송 ≈ 2배 토큰) | 교정 메시지 자체가 방향("형식만 고쳐 다시")을 주므로 우려와 정면 충돌 | 보류 — B 의 측정(재시도 성공률, §3의 P10 reasonCode 로 산출)이 낮으면 재검토 |

- B 구현 위치: `runAttempt`(1700 부근)가 새 시도를 만들기 직전, 작업 장부의 **마지막 시도**(attempts[attempts.length-1] — 새 시도의 attemptId 는 attempts.length 이므로 바로 앞 시도)가 `phase:"failed"` ∧ `failureStage ∈ {response, validation, conversion}` 이면 그 `failureCode`·`droppedItems` 를 기계 분류 요약 `ctx.priorRejection` 으로 어댑터 입력에 싣고, `buildEnrichPrompt`가 "## 지난 답에서 제외된 항목(자료)" 절을 붙인다. `retryFrom` 은 보지 않는다(라우팅 경계 전용 — 재개 시 attempts.length 로 갱신돼 그 뒤 시도가 없다, 1579·extension.ts 755). 편집 중 충돌로 빠진 항목(detail.fileChanged === true)은 담당 잘못이 아니므로 요약에서 뺀다(전부 그런 경우 절 자체를 붙이지 않음). 경로별 분기(1563-1587 자동 재시도·2290-2320 재개 failed 분기·수동 재시도)에 손대지 않는다 — 어느 경로로 왔든 같은 장부 사실을 본다. D4-2 가 (ㄴ)이면 마지막 재개 사건(`resumes` 끝 항목)이 manual 일 때만 싣지 않는다.
- 시험: 정밀형 시도 0 이 validation 거부 → 자동 재시도(retryFrom=1)의 시도 1 프롬프트에 자료 절 존재 · 기본형 재개 경로 재호출에도 존재 · 수동 재시도는 D4-2 값에 따라 · call 단계 실패 뒤에는 없음 · fileChanged 항목만 빠진 경우 절 없음 · 프롬프트에 파일 본문·자유문 없음(기계 분류 키만).
- **D4-2(사용자 결정 — 검토 1판 보완으로 승격)**: 사용자가 누른 '다시 시도'는 (ㄱ) 같은 자료를 싣는다(권장 — 사용자 재시도가 더 값비싸고, 자료는 기계 분류뿐) / (ㄴ) 깨끗한 재호출로 둔다(이전 실패에 조건화되지 않은 답을 원할 때). 화면 문구도 갈린다: (ㄱ)이면 "지난 제외 이유를 붙여 다시 묻습니다", (ㄴ)이면 "처음처럼 다시 묻습니다".
- 하지 않는 것: 새 실패 분류 신설·재시도 횟수 증가·프롬프트 지시문 추가·기본형을 유료 담당의 자동 재시도 분기에 편입(무과금 재개 경로가 이미 같은 역할).

## 7. 같은 순서를 쉬운 말로

1. 먼저 **재는 것부터** 한다. 자동 보강이 담당에게 몇 번 물어 답을 받았는지(답 없이 끝난 호출은 따로, 자동으로 한 번 더 물을 여지가 남았는지, 사용자가 몇 번 다시 시도했는지, 편집 중 충돌로 다시 물은 게 있는지)와, 담당이 낸 답의 인용이 우리가 보낸 발췌 안에서 나왔는지를 카드에 두 줄로 보여 준다. 아무 동작도 바꾸지 않는다.
2. 그 수치를 보고 **읽게 만드는 장치**를 켠다: 보낸 발췌 안에서 따온 인용만 받아 주고, 발췌 자체를 '파일 첫머리'가 아니라 '이번에 고친 부분 주변'으로 바꾼다. git 이 없거나 새 파일이면 예전처럼 첫머리를 보내되 제목에 그렇게 적는다.
3. 그다음 **얼마나 보낼지**를 프로젝트마다 고를 수 있게 한다(검증 왕복 상한과 같은 자리, 같은 버튼 방식). 권장 10파일·대형 15파일 같은 프리셋 수치는 1번의 측정을 보고 확정한다.
4. 마지막으로 되묻기는 새 호출을 만들지 않고, 이미 있는 '한 번 더 시도'에 "지난 답의 몇 번째 항목이 어떤 종류의 이유로 빠졌다"는 **기계 분류만** 붙인다. 정밀 담당에게 따로 한 번 더 묻는 방식은 비용이 두 배이고 방향을 주는 셈이라 보류한다.
