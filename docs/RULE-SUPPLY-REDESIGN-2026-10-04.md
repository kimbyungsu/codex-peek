## 요약 (사용자용)

**무엇이 문제였나.** 새 프로젝트를 이 하네스로 시작하면, 수칙서를 누군가 손으로 써서 승인하기 전까지 "수칙 후보를 모으는 장치"가 통째로 꺼져 있다. 그 사이 사용자가 "이번엔 내 폰으로 시험하는 게 목표야"처럼 계속 지킬 기준을 열 번 말해도, 그 말이 후보로 올라갈 길이 없다. 선택지에 직접 쓴 말은 아예 사용자 말로 인정되지 않는다. 첫 수칙서를 제안해도 대시보드에 승인 버튼이 뜨지 않는다. 덤으로 마감 글 형식 검사가 같은 글을 몇 번씩 다시 내보내고, 정찰은 커밋된 변경을 못 본다.

**무엇을 바꾸나(네 묶음).**
1. **빈 수칙서로 시작** — 수칙서가 없어도 "항목 0개짜리 수칙서"가 있는 것처럼 기록·판단 관문·후보 접수를 켠다. 검증자의 차단을 내리는 일(강등)은 사용자가 첫 도장을 찍기 전까지 하지 않는다. 첫 후보에 도장을 찍으면 수칙서 파일이 자동으로 만들어진다.
2. **사용자 말을 후보로** — 선택지에 직접 쓴 답도 사용자 말로 남긴다. 아직 분류하지 않은 사용자 말은 대기열에 쌓이고, 캠페인이 끝날 때 독립 실행이 대기열을 읽어 "계속 지킬 기준"을 골라 **수칙서 / 사용자 규칙 칸 / 결정 기록** 중 맞는 자리로 후보를 낸다. 사용자는 도장만 찍는다. 검증자에게는 도장 전 사용자 말을 넣지 않는다.
3. **마감 글 분리** — 기계용 마감 기록은 명령으로 제출하고, 사용자에게 보이는 답은 평이한 요약만 남긴다. 형식이 틀려도 같은 글이 화면에 되풀이되지 않는다.
4. **정찰·지도** — 정찰이 "지난 지도 이후 커밋된 변경"까지 보게 하고, 요약 누락·지도 파일 목록 표시를 고친다.

**하지 않는 것.** 매 턴 "수칙으로 올려라" 같은 문장 추가 · 검증자에게 도장 전 사용자 말 넣기 · 문구 감지기 · 사용자 규칙 준수를 검증자에게 넘기기 · 검증 모드 변경 제안.

## §1 설계 원칙 (이 문서의 헌법)

**사용자가 해 온 판단을 대신하지 않고, 사용자가 판단할 재료와 자리를 하네스가 만든다.** 개발 작업공간에서 설계자인 사용자가 직접 해 온 일(초판 작성, 검증 고리를 보고 "범위 밖"이라고 정하기, 반복 지적을 기준으로 올리기)을, 하네스 내부를 모르는 사용자도 도장 한 번으로 할 수 있게 한다.

- **R1 문장 0**: 구현자·검증자 지시문에 새 "하라" 문장을 더하지 않는다(§4-B). 새로 생기는 글은 상태 줄(상태 서명 1회·예산 안)과 판단 재료(데이터)뿐이다.
- **R2 권위 경계 불변**: 도장 전 사용자 말·후보는 판정을 만드는 입력에 들어가지 않는다(CONSTRAINT-CAPTURE 119~124). 구현자 반박만으로 통과가 생기지 않는다(REJUDGE P6).
- **R3 승인 전 원문 경계**: **승인 전** 사용자 원문(턴 원문·직접 입력 기록·분류 입력)은 구현 턴과 같은 회사에게만 간다(서고 선별과 같은 규칙). **승인 뒤** 문장은 그 자리의 기존 전송 정책을 따른다 — 수칙서 항목은 검증자에게, 사용자 규칙 칸은 구현자에게, 결정 기록은 정리 담당(탐색 담당 회사 — D-2026-09-06의 "탐색 담당 선택=동의" 정책·PRIVACY.md)에게 간다. 승인 화면은 자리마다 "승인하면 이 문장이 누구에게 전달되는지"를 보여 준다.
- **R4 판단은 LLM, 계기는 형태**: 무엇이 계속 지킬 기준인지는 LLM이 판단한다. 하네스는 "언제 판단을 부를지"를 형태 신호(캠페인 마감·미분류 사용자 말 존재)로만 정한다. 문구 패턴 금지.
- **R5 소수정예·자리 구분**: 후보 자격은 성격(관통하는 기준)이다. 후보는 성격에 따라 자리를 나눈다 — 검증이 무엇을 막을지(수칙서) / 구현자가 어떻게 일하고 보고할지(사용자 규칙 칸) / 이번 프로젝트의 선택(결정 기록).
- **R6 사용자 설정 불간섭**: 검증 모드·예산 같은 사용자 옵션을 바꾸거나 바꾸자고 하지 않는다.

## §2 묶음 1 — 빈 수칙서(0세대)로 시작 + 첫 도장

### 2-1. 0세대 정의
- 승인 지문(envelopeHash)도 수칙서 파일도 없는 작업공간은 **0세대**로 본다.
- **0세대 지문(`GEN0_HASH`) = 첫 초안 작성기가 "빈 코어 수칙서"(필수 `schema:"verify-envelope-v1"` 포함 — contract-lib.js:3801·3926)를 저장할 때의 실제 저장 바이트의 SHA-1.** 손으로 적은 상수가 아니라 작성기와 같은 직렬화 함수로 계산하고, "계산값 = 빈 코어를 실제로 저장한 파일의 지문"을 시험으로 고정한다(승인 지문이 실제 저장 바이트 기준이기 때문). 40자리라 동결 기록 판독(contract-lib.js:5770 — null 또는 40자리만 인정)을 바꾸지 않고 통과한다.
- 0세대 지문은 **계약에 쓰지 않는다**(ab-2 — 판독 시 파생). 동결 기록·지적 장부·후보 행에는 `envelopeHash: GEN0_HASH`와 함께 `virtualGen: true`를 남겨, 사용자 승인과 구분한다(입장 심사·승인 판독은 virtualGen 행을 "승인 경계"로 쓰지 않는다).
- 첫 도장에서 코어를 정확히 빈 상태로 승인하면(항상 차단 후보를 모두 서고로 보낸 경우) 실제 코어 파일 지문이 GEN0_HASH와 같아진다(위 정의에 따라 같은 바이트). 이때는 파일과 계약 지문이 있으므로 **정식 승인**(virtualGen 아님)이고, 세대 지문이 바뀌지 않으므로 0세대 지적은 같은 세대로 그대로 이어진다(2-3 4의 세대 전환이 일어나지 않는 경우).

### 2-3. 첫 도장 — 0세대 후보에서 수칙서 파일까지
지금 후보 채택은 "이미 승인된 코어가 있다"를 전제로 서고 개정 초안을 만든다(E3). 0세대에는 그 전제가 없으므로 **첫 초안 전용 함수**를 둔다.
1. **첫 초안 만들기(`draftEnvelopeInitial`)**: 입력=선택된 0세대 후보들. 기준=GEN0_HASH(파일이 아니라 계산값과 대조 — 코어 파일이 생겨 있으면 거절하고 기존 개정 경로로 보냄). 출력=코어 제안본(baseHash=null). 후보의 자리별 목적지:
   - 범위 밖·지원 환경 후보 → 코어의 해당 축.
   - 항상 차단 후보 → **사용자가 항상(코어)/관련될 때(서고) 중 고른다**(REJUDGE P5 — 추천값만 표시, §7 D6).
   - **첫 초안에는 코어로 가는 후보만 결속한다.** 서고를 고른 후보는 첫 초안에 결속하지 않는다 — 결속된 후보는 승인 순간 `applied`로 종결되고(contract-lib.js:4134~4138) 이월에서 빠지며(4885), 후속 서고 초안은 현재 세대의 proposed 후보만 받기 때문이다(5183~5187).
2. **표시**: 대시보드 수칙 카드 판독(readEnvelopeView)은 파일·지문이 없을 때 null을 돌려주기 전에 ① 제안본이 있으면 "첫 수칙서 초안 승인 대기" 카드, ② 0세대 후보가 있으면 후보 목록 카드(채택=첫 초안 만들기)를 띄운다(1163의 조기 반환을 제안본·후보 확인 뒤로).
3. **승인(도장 두 번까지)**: 첫 도장은 기존 최초 작성 경로(contract-lib.js:3968 baseHash=null · 4091 · 4104)로 코어 파일을 쓰고 계약 envelopeHash를 기록한다(정식 1세대 — 코어 축이 비어 있어도 된다). 서고를 고른 후보는 이 전이 안에서 기존 carry-forward로 **새 세대의 proposed 후보로 정확히 1회 재발급**되고, 대시보드가 곧바로 "서고로 올리기" 초안(기존 draftEnvelopeRevision target archive)을 제시해 **두 번째 도장**으로 서고에 들어간다. 두 번째 도장 전에 중단돼도 후보는 proposed로 남는다(분실 없음).
4. **세대 전환 규칙(첫 승인 순간)** — 기존 세대 전환과 같게 다룬다:
   - 0세대 **열린 지적은 같은 findingId로 새 세대에 옮기지 않는다.** 지적 ID는 세대를 재료로 만들어지고(contract-lib.js:5344~5347) 활동 회차·처분 조회는 세대를 구분하지 않으므로(5369~5385·5407~5417), 같은 ID 이월은 옛 처분을 새 재등장에도 유효하게 만든다(검증 2회차 반례: 0세대 round 3 처분 뒤 새 세대 round 1 재등장 → 미판단 0). 또 통과 종결은 `o.round < roundNo` 조건이라(codex-bridge.js:4610) 옛 회차를 지닌 이월 지적이 새 세대 첫 통과에서 닫히지 않는다.
   - 대신 0세대 열린 지적은 새 세대 판단 관문에서 빠진다(contract-lib.js:5330 세대 필터). **구현 정정(묶음 1 구현 검증 1회차 blocker②)**: 관문은 '직전 검증의 동결 지문'을 읽으므로 그대로 두면 첫 도장 뒤 다음 검증 시작 전까지 0세대 지적을 계속 요구한다(승인 세대끼리의 재승인도 같은 동작 — 그쪽은 이번 범위 밖·종전 유지). 그래서 직전 동결이 0세대 표식(virtualGen)이고 계약에 정식 승인 지문이 생겼으면 관문·지적 판단 명령·대시보드 후보가 그 새 지문을 쓴다(codex-bridge.js judgeGenFor·candidatesGenOptsFor). 조용히 사라지지 않도록 **첫 도장 확인 창에 "0세대 열린 지적 N건(판단 완료 M · 미판단 K)"과 목록을 보여 준다.** 장부의 0세대 행은 그대로 남는다(덧붙이기 전용 — 이력). 다음 검증부터 검증자가 새 세대 기준으로 코드를 다시 보므로, 남은 문제는 새 세대 지적으로 다시 나온다.
   - 0세대 **후보**: 코어로 채택된 것은 첫 초안에 결속(adopted→applied), 서고 선택분·미처리분은 기존 carry-forward 규칙(user-constraint와 동형 — 새 세대에 정확히 1회 재발급)으로 proposed 이월.
   - 이월은 첫 승인 전이와 같은 잠금 안에서 처리하고, 실패하면 승인 전이 복구(WAL) 대상이 된다(ab-5·ab-6).
5. 대시보드 6711 문구를 실제 흐름에 맞춘다(예: "아직 없음 — 대화에서 생긴 기준 후보가 여기 올라오면 도장을 찍어 시작해요").
- E2의 책임 공백은 이 묶음이 메운다 — 첫 수칙서는 "누가 쓰나"가 아니라 "0세대 후보에 도장 → 첫 초안 자동 작성"이 된다.

### 2-4. 개정이 필요한 정본
- VERIFY-GOVERNANCE §3.1 활성 행렬(동결) — "부재+v1=현행 그대로" 행을 "부재=0세대(v2 요구·기록·관문, 강등 없음)"로 개정. **사용자 결정 필요(§7 D1).**
- MEMORY-AUTHORITY A-6 — "첫 수칙서 부트스트랩은 후보 고지 흐름 소관" 문장을 이 설계로 대체.
- CONSTRAINT-CAPTURE §3-4 "비활성=후보 대신 안내" — 0세대 접수로 개정.

### 2-5. 기존 프로젝트에 미치는 영향(하위 호환)
- 수칙서 없이 쓰던 프로젝트는 업데이트 후 첫 검증부터 v2 서식·판단 관문이 켜진다. 판단 관문은 "열린 지적마다 한 줄 판단"을 요구하므로 마찰이 생긴다 — 이것이 의도된 "되받는 단계"다. 대시보드·릴리스 노트에 이 변화를 알린다.
- 검증자 쪽 정적 지시가 v2 고정 산문만큼 늘어난다(세션 1회).
- 수칙서가 이미 있는 프로젝트는 변화 없음(0세대 판정 조건 불충족).

## §3 묶음 2 — 사용자 말을 후보로

### 3-1. 원문 인정 범위 확장 (E5)
- 선택지 도구에 사용자가 **보기 이름과 다른 글**을 쓴 답은 그 턴의 **별도 원문 기록**으로 남긴다(사용자 글 그대로·턴 앵커·작업공간 키·세션 결속·기록별 지문). 문자열 "Other"만 있는 답은 제외한다.
- 판별 재료(실측): Claude Code 대화 기록은 선택지 결과를 `toolUseResult = { questions:[{question, header, options:[{label, description}], multiSelect}], answers:{<질문>: <답 글>} }`로 저장한다(LTE 대화 11936·12575행). 답 글이 그 질문의 보기 label(복수 선택이면 label 조합)과 다르면 직접 입력이다 — 내용 해석 없는 형태 판별.
- **턴 원문 파일은 고치지 않는다** — 검증 작업이 시작 때 그 파일 지문을 동결하고(codex-bridge.js:3162~3165) 불일치면 후보를 전량 거절하기 때문이다(contract-lib.js:4726).
- 원문 대조(constraintAdd·회수)는 "턴 원문 **또는** 그 턴의 직접 입력 기록"에서 연속 구절을 찾는다.
- 받는 시점: ① 도구 사용 뒤 훅(PostToolUse, matcher `AskUserQuestion`)에서 받는다 — 공식 문서상 선택지 도구는 내장 도구라 이름으로 걸 수 있고 훅 입력에 session_id·transcript_path가 있다. 다만 훅 입력의 tool_response가 위 toolUseResult와 같은 구조인지는 문서에 없다(§8 Q1 — 구현 첫 단계에서 실측). ② 그게 안 되면 다음 훅 시점(다음 입력 제출 또는 종료)에 대화 기록을 **수집 커서** 이후부터 읽어 수집한다 — 공식 문서가 훅 시점의 대화 기록은 늦게 쓰일 수 있다고 하므로 늦게 나타난 답은 다음 기회에 수집된다. 늦게 들어온 답도 3-2의 대기열에 들어가므로 분류에서 빠지지 않는다. 어느 쪽이든 이미 시작된 검증에는 소급하지 않는다.

### 3-2. 미분류 대기열 (재처리 계약)
- 모든 사용자 말(턴 원문 스냅샷 + 직접 입력 기록)은 수집되는 순간 **미분류 대기열**에 들어간다(작업공간·저장소 표식 결속, 덧붙이기 전용 상태 행: queued → classified | held).
- 분류 실행의 입력은 "이번 캠페인"이 아니라 **대기열의 미분류 항목(오래된 것부터, 한 번에 다룰 크기 상한까지)**이다. 그래서:
  - 최소 간격·하루 상한으로 **건너뛴 계기**의 말은 대기열에 남아 다음 계기에 처리된다.
  - 실행 **실패·시간 초과**면 그 묶음은 queued로 남고 재시도 횟수만 올라간다.
  - **늦게 수집된** 답(3-1 ②)도 대기열로 들어와 다음 계기에 처리된다.
  - 한 번에 다 못 읽으면 나머지는 다음 계기로 넘어간다.
- 재시도 상한을 넘은 항목은 held로 바꾸고 대시보드에 "분류하지 못한 사용자 말 N건"으로 보인다(조용한 누락 금지). 사용자는 그 원문을 보고 직접 후보로 올리거나 버릴 수 있다.
- 명령 `classify run`으로 수동 실행 가능(정리 담당의 `curate run`과 같은 형태).

### 3-3. 분류 실행 (누가 판단하나)
- **독립 분류 실행**이 판단한다. 판정을 만드는 검증자에게는 넣지 않는다(R2). 실행 담당은 **서고 선별과 같은 규칙 — 구현 턴과 같은 회사**(selector-runner 페이지 방식, R3). 정리 담당(탐색 담당 회사)에게 승인 전 사용자 원문을 넘기지 않는다.
- 입력: 대기열의 사용자 말(민감 형태 생략 규칙 적용) + 현재 승인 수칙·사용자 규칙 칸·결정 기록의 제목(중복 방지용). 변경물·검증 결과는 넣지 않는다(판단 대상은 사용자 말뿐).
- 출력: 후보 0~N개(상한 소수). 각 후보 = 사용자 원문 연속 구절(quote) + 자리(3-4) + 왜 계속 지킬 기준인가(120자) + 근거 항목 id. quote는 원문 대조를 통과해야 접수(작문 차단). 근거 없는 후보는 받지 않는다(정리 담당의 no-ref 규칙과 동형).
- 계기(R4): **캠페인 마감**(검증 통과 마감 또는 상한 소진 마감) 때 대기열에 미분류 항목이 있으면. 비용 상한: 최소 간격·하루 상한·대기열 비면 무호출. 값은 **사용자 결정(§7 D2)**.

### 3-4. 후보의 세 자리 (R5)

|---|---|---|

- 후보 표면은 대시보드 후보 목록 하나(자리 표시와 전달처 표시만 다름). 도장=승인/안 올림. 안 올림은 같은 세대에서 재제안 억제(기존 거부권).

### 3-5. 기존 경로와의 관계
- 구현자 상신(constraint add)은 그대로 둔다(3-1로 직접 입력도 대조 가능). 최상위 도움말 목록에 constraint·envelope-proposal을 올린다(주입 아님 — R1).
- 정리 담당은 변경 없음(재료·팔·계기 그대로). 결정 기록 자리로 들어온 행은 정리 담당이 기존처럼 힌트로 읽는다.
- 검증자 쪽 [제약 후보 v1] 규칙(contract-lib.js:3693)은 유지하되, 원문이 자동으로 가지 않으므로 이 경로의 기여는 구현자가 요청에 옮겨 적은 범위에 한정된다는 사실을 문서에 명시한다.

### 3-6. 단계 범위의 구현자 노출
- 승인된 "범위 밖·지원 환경" 항목은 지금 구현자에게 판정 도착 때 번호로만 보인다([되받아침 재료]). 짧은 목록을 구현자 쪽 정적 블록(세션 1회·세대 결속 — 지금은 항상 차단 칸만)에 함께 싣는 안이 있다. 수칙서가 소수정예라 크기는 작지만 정적 블록이 커진다 — **사용자 결정(§7 D3)**.

### 3-7. 구현자에게 남는 글
- 후보가 도장 대기 중일 때 상태 줄 1회: "사용자 확인 대기 기준 N건 — 대시보드". 기존 "그 상태에 1회만" 안내와 같은 형태, 상황 안내 550자 예산 안(contract-inject.js:224~228).

## §4 묶음 3 — 마감 글 분리 (E7)

- 검증 상한 마감(검증 상한 인계)의 기계용 기록은 **명령으로 제출**한다(예: `closing submit --file <마감.md>`). 명령이 기존 검사기(validateCapHandoff — verify-cap-handoff.js:302)로 **제출 시점의 현재 문맥**(최신 근거·열린 보관함 영수증·결정 상태 — capHandoffContext)으로 검사하고, 통과하면 캠페인·턴에 결속된 마감 기록을 저장한다. 실패 사유는 명령 결과로 돌아오므로 **사용자에게 보이는 답이 되풀이되지 않는다.**
- 종료 관문(verify-guard.js)은 답 본문을 파싱하는 대신 결속된 마감 기록을 읽어, **종료 시점의 현재 문맥으로 같은 검사기를 다시 돌린다**(제출 뒤 보관함·결정 상태가 바뀌었으면 기록이 무효 — 재제출 요구는 명령 안내로만). 잔여 재검증 마커 기록(verify-guard.js:299~308)은 지금과 같은 조건으로 남기며, 그 기록에 실패하면 종료를 인정하지 않는다(현행과 동일).
- 사용자에게 보이는 답에는 평이한 요약 + "마감 기록 제출됨(대시보드)" 한 줄만 둔다.
- 마감 기록의 의미(네 절 행선지·결정 장부 표기·잔여 위험·경고등)는 그대로다. 기계 번호(R<n>-F<m>)는 기록 안에만 남는다.
- [계약점검] 블록은 답 자체에 대한 자가 점검이므로 답 끝에 그대로 둔다(RULE-COMPLIANCE 불변).
- ab-3: 마감 기록은 검증 통과 증명이 아니며 종료 조건의 다른 축과 AND — 통과 위조 경로가 늘지 않는다.

## §5 묶음 4 — 정찰·지도

- **E8 정찰 변경 범위**: git 저장소일 때 씨앗 = `직전 지도 기준 커밋..HEAD` 변경 파일 ∪ 작업트리 변경, diff = 기준 커밋 대비 diff(작업트리 포함). 기준 커밋이 없어졌으면(이력 재작성) 지금 방식으로 떨어지고 그 사실을 보고서에 적는다. 크기는 기존 상한 안.
- **E9 요약 추출**: 항목 단위로 읽는다. 항목 = 'high' 표기가 있는 **목록 머리 줄**(번호·불릿)과, 그보다 **깊게 들여쓴** 이어지는 줄(하위 불릿·연속 문장). 항목은 **같거나 얕은 들여쓰기의 다음 목록 머리**·제목·구획 표기·빈 줄에서 끝난다 — 머리 바로 아래의 하위 불릿("   - 경로: …", 2026-09-27 21:10 보고서 3~4행)은 같은 항목에 포함된다. 줄 수 상한·구획 규칙(①~④만)은 유지.
- **E10 파일 목록**: 먼저 표시를 바로잡는다 — MAP.md·status의 수치를 "생성 당시 순회 N개(날짜)"로 표기. 정본 갱신(지문에 포함되는 값)은 별도 결정(§7 D4).
- **E11 일지 갈라짐**: 자동 병합은 하지 않는다(설계 불변). 이미 있는 병합 후보 계산(ledger-events-core.js:273~283)을 대시보드에 보이게 하고, 갈라진 묶음 수를 건강 줄에 낸다.
- **조사 항목(이 설계 범위 밖)**: 정찰이 본 파일이 지도 노드로 편입되지 않는 원인(LTE BootReceiver·TileText·Controller·NetWatch).

## §6 하지 않는 것 (명시)
- 구현자·검증자 지시문에 "사용자 말을 수칙으로 올려라" 같은 문장 추가(§4-B).
- 판정을 만드는 검증 입력에 도장 전 사용자 말·후보 동봉(CONSTRAINT-CAPTURE 119~124).
- 승인 전 사용자 원문을 구현 턴과 다른 회사로 보내기(R3) — 정리 담당·정찰 담당 재료로 넘기지 않는다.
- 문구 패턴 검출기·키워드 목록.
- 사용자 규칙 준수 판정을 검증자에게 넘기기(RULE-COMPLIANCE §4 사용자 기각) — 2026-10-03 분석 보고에서 낸 "규칙 점검 독립 채점" 안은 이 결정과 충돌하므로 철회한다.
- 일지 자동 병합·도장 없는 자동 승격.
- 검증 모드·예산 등 사용자 옵션 변경 제안.

## §10 ab 경계 자기 점검
- ab-1: 직접 입력 기록·대기열·분류 후보·0세대 후보·후보 이월 기록은 작업공간 키·턴 앵커·저장소 표식에 결속 — 다른 프로젝트 장부 오귀속 없음.
- ab-2: 계약 필드 추가 없음(0세대 지문은 파생 상수). 사용자 규칙 칸은 도장 받은 원문 덧붙이기만 — 기존 글 변경·삭제 없음.
- ab-3: 0세대는 승인 흉내가 아니다(virtualGen·강등 없음). 일반 반박은 판단 기록일 뿐 강등·통과를 만들지 않고, 범위 밖 번호 반박(도장 뒤)도 강등이지 통과가 아니다(REJUDGE P6). 마감 기록은 통과 증명 아님·종료 시 재검사.
- ab-4: 분류 실행은 구현자·검증자 세션과 분리된 독립 실행. 사용자 규칙 준수 판정은 계속 구현자 자가 점검(검증자 무관).
- ab-5: 모든 새 기록은 덧붙이기 전용. 0세대 지적 행은 첫 도장 뒤에도 장부에 남는다(관문에서 빠질 뿐). 후보 이월은 승인 전이 잠금·복구 안에서.

- ab-7: 승인 전 사용자 원문은 민감 형태 생략·구현 턴과 같은 회사로만(R3). 승인 뒤 문장의 전달처는 승인 화면에 표시.
- ab-8: 해당 없음.
