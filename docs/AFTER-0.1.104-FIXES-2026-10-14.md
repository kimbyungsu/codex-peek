## 요약 (사용자용)

**남은 단계는 셋, 확인 하나.**
1. **도우미 Claude 호출 바로잡기(설계 A)** — 사용자 말 분류가 대부분 버려지고 있다(이 작업공간 23번 중 17번). 그래서 정정 7묶음을 다 넣었어도 이 작업공간에서는 수칙 후보가 하나도 나오지 않는다. 원인은 하네스가 도우미 Claude를 부르는 방식에 있고, 같은 방식을 서고 선별·정리 담당·정찰·자동 보강(Claude 가 맡을 때)도 쓴다. 선별 등은 답 모양이 단순해 버티고 있을 뿐, 같은 결함(옛 판 사용·사용자 지침이 섞임·실행할 때마다 사용자 대화 기록에 대화가 하나씩 남음)을 안고 있다. Claude 도우미 실행기 하나를 만들어 모두 옮기고(분류·선별·정리 먼저), 잘 되던 것이 계속 잘 되는지 시험한다. 로그인 파일은 복사하지 않는다.
2. **Codex 훅 경보 상태 구분(설계 B)** — 훅을 설치·신뢰한 뒤 아직 Codex 대화를 쓰지 않았을 뿐인데 빨간 오류가 뜨고, 사용자가 Codex에서 대화를 열거나 질문해야만 풀린다. "아직 확인 전"과 "실제로 실패"를 나눠, 확인 전에는 빨강 대신 "첫 사용 때 자동 확인"만 보이게 한다.
3. **정찰·지도(10월 4일 재설계 묶음 4)** — 설계는 이미 있다(그 문서 §5). 위 둘과 독립.
- **정정 효과 확인(확인 C)** — 사용자가 따로 써 보실 일이 아니다. 설계 A를 고친 뒤 구현 담당이 이미 쌓인 사용자 말을 기록에 남기지 않는 시험 실행으로 다시 분류해, 지나치게 많고 불필요하던 후보가 줄었는지 표로 보인다.

### 1-2 결론

**필요하다.** 분류가 고장(이 작업공간에서 수칙 공급 고리 전체를 멈춤)이고, 원인 넷(옛 판 · 사용자 지침 섞임 · 형식을 프롬프트에만 맡김 · 실행 기록 남김) 가운데 셋(옛 판·지침 섞임·기록 남김)은 여섯 곳 모두에 있다(①② 실측 · ③~⑥ 코드상 같은 실행 인자). 그래서 **Claude 도우미 실행기 하나**(실행 파일 고르기 + 격리 실행 + 답 꺼내기)를 만들어 여섯 곳이 같은 실행 파일 고르기를 쓰고, ①~⑤는 격리 실행까지 그쪽으로 옮긴다. 형식을 틀로 강제하는 일(A3)은 기계용 JSON 답을 받는 곳(①②③)만.
- 묶음 A-1: 실행기 + `runSelectorPage` self 팔(①②③). 시급(분류 고장).
- 묶음 A-2: ④ 정찰 · ⑤ 자동 보강을 같은 실행기로(격리·실행 파일만 — 답 모양은 그대로). ⑥ Claude 검증 담당은 파일을 읽어 검증해야 해서(도구·프로젝트 폴더 필요) 실행 파일 고르기(A1)와 실행 기록 남기지 않기만 적용하고, 안전 모드 적용 여부는 검증 동작이 바뀌는 별도 결정이라 §4 보관함.
- ②③④⑤⑥을 옮기는 이유는 "지금 고장나서"가 아니라 "같은 숨은 결함을 안고 있어서"이며, 잘 되던 것이 계속 잘 되는지 시험으로 확인한다(§1-7).

### 1-3 바꾸는 것

**A1 실행 파일 고르기** — 아래 순서로 첫 번째로 쓸 수 있는 것.
0. 시험·사용자 지정 덮어쓰기 환경값 `CODEX_BRIDGE_CLAUDE_BIN`(이미 ⑥에 있음 — codex-bridge.js:2748) — 있으면 맨 앞.
1. 지금 이 대화를 돌리는 Claude Code 가 알려 주는 자기 위치: 환경값 `CLAUDE_CODE_EXECPATH`(이 대화의 도구 실행 환경에서 실측). 분류 자동 실행·정리 담당 실행은 Claude 쪽 입력 제출 훅이 띄우고(contract-inject.js:249·251 → classify.js:936 등) 검증 선별은 ask-start 를 부른 도구 실행 환경을 물려받으므로 이 값이 이어질 것으로 보나, 훅 쪽은 Q1 로 확인.
2. 훅이 마지막으로 기록해 둔 위치: `~/.codex-bridge/claude-bin.txt` — Claude 쪽 훅이 돌 때 1의 값이 있으면 기록(Codex 의 codex-bin.txt 와 같은 방식). 확장이 직접 띄우는 실행처럼 1이 없는 경우를 위해(예: 자동 보강 — extension.ts:791 은 확장 프로세스 환경으로 띄움).
3. PATH 의 `claude`.
- "쓸 수 있다" = 파일이 있고, 필요한 기능(아래 A2 의 안전 모드·정해진 틀·기록 안 남김·도구 끄기)을 지원함. 지원 여부는 그 실행 파일의 도움말에서 확인하고 (경로+수정 시각) 기준으로 캐시. 확장 업데이트로 옛 경로가 사라지면 다음 후보로 넘어가고, 다음 훅이 새 위치를 기록한다.
- 새 기능을 지원하는 후보가 하나도 없으면 A4 로 간다.

**A2 실행 방식** — `-p --output-format json --safe-mode --tools "" --strict-mcp-config --no-session-persistence` (+ ①②③ 만 `--json-schema <호출자 틀>`)
- 안전 모드: 사용자 지침(CLAUDE.md)·훅·MCP·설치 플러그인·사용자 지정 명령 등 사용자 맞춤을 끄고, 로그인·모델 선택·권한은 평소대로 둔다(2.1.296 도움말 문구). 기본 시스템 지시는 바꾸지 않는다. → 로그인 파일을 임시 폴더로 복사하지 않는다 — 사본이 남거나 로그인 갱신 때 원본과 어긋나는 경로가 없어진다(사용자 설정 폴더를 그대로 쓰므로 인증·설정이 바뀔 위험이 전혀 없다는 보장은 아니다). 앞선 분석의 "임시 설정 폴더+로그인 사본" 안은 이것으로 대체한다.
- 기본 시스템 지시는 유지한다(시스템 지시를 통째로 바꾼 시험에서 분류 품질이 떨어졌던 관측 — 2026-10-13 repro_sysprompt).
- 작업 폴더 = 빈 임시 폴더(끝나면 삭제) → 프로젝트 지침·자동 기억과 무관.
- 환경값: 현재 대화에 묶는 값(세션 id·부모 대화 연결 통로·진입점 표식·자식 세션 표식 등)만 빼고, 로그인 위치(CLAUDE_CONFIG_DIR)·API 키·프록시는 유지(⑥이 이미 쓰는 규칙과 같은 방향 — codex-bridge.js:2759~2762). A1-1 값은 빼기 전에 읽는다. 셸 없이 직접 실행.

## §2 설계 B — Codex 훅 경보 상태 구분

### 2-1 지금
Codex↔Codex 모드에서만 판정한다(extension.ts:3495). 신뢰 조회가 통과하면, 연결된 구현 대화의 마지막 차례에 Codex 가 실제로 훅을 실행한 기록(대화 시작·재개, 입력 제출, 도구 뒤, 차례 종료 중 하나 — codex-hook-health.ts:70, codex-hook.js:498~506)을 요구한다. 기록이 아예 없으면 heartbeat-missing, 옛 차례 기록만 있으면 heartbeat-stale → 둘 다 빨간 오류(extension.ts:3273~3279, severity error). 이 판정은 화면 전용이다(경보·온보딩 4단계 — extension.ts:2910~2912·8948). 무엇을 막지 않는다.

### 2-2 결함
- 훅을 설치·신뢰한 뒤 아직 Codex 구현 대화를 쓰지 않은 상태 — 아무것도 실패하지 않았다 — 도 같은 빨강이다.
- "현재 구현 대화"가 오래된 대화일 수 있다(2026-10-14 이 작업공간: 7월 대화).
- 풀리는 길이 사용자 행동(Codex 대화 열기·질문)뿐이고, 문구도 그 행동을 요구한다.

### 2-3 판정 (네 갈래)
기준 시각 T = **설치기가 지금의 Codex Peek 훅 항목을 훅 파일에 쓰기 직전에 잡은 시각**. 원칙: T 는 새 훅이 보이기 시작한 순간보다 **늦으면 안 된다** — 틀리더라도 이른 쪽으로 틀려야 한다(이르면 '실패'가 더 많이 보일 뿐 숨지 않음).
- 새 설치부터: 설치기가 훅 파일 쓰기 **전에** 시각을 잡아 소유 기록에 새 칸(쓰기 시작 시각)으로 남긴다. 지금의 installedAt(codex-plugin-install.js:224)은 훅 파일 쓰기(188) **뒤**에 잡히므로 T 로 쓰지 않는다(2026-10-15 2회차 지적 f-8a81f25a: 훅 파일 공개 → 그 사이 차례 시작 → installedAt 생성 순서면 그 차례가 '확인 전'으로 낮춰짐).
- 쓰기 시작 시각 칸이 없는 옛 기록: 같은 설치가 훅 파일 쓰기 직전에 만든 백업 파일 이름의 시각(`hooks.json.bak.<시각>` — codex-plugin-install.js:180 은 쓰기 전에 이름을 정함)을 쓴다 — installedAt 이하인 백업 중 가장 늦은 것. 그 백업이 더 이른 설치의 것이어도 T 가 더 일러질 뿐이라 원칙에 맞는다. 2026-10-15 실물: 백업 이름 시각 2026-10-09T23:19:50.123Z ≤ 훅 파일 수정 23:19:50.125Z ≤ installedAt 23:19:50.125Z(백업 파일 자신의 수정 시각은 .124Z). 그런 백업이 없으면(처음 설치라 이전 파일 없음) "T 를 정할 수 없음".
- 따라서 T 뒤의 차례는 "새 훅이 돌았어야 하는 차례"이고, 경계에서는 실패 쪽으로 판정한다(차례 시각 = T 도 '뒤'로 본다).
- T 는 하네스가 신뢰 조회 결과를 받은 시각이 아니다(2026-10-15 1회차 지적 f-8a81f25a: 조회 시각은 실제 설치·신뢰보다 늦어, 그 사이 실패한 차례를 '확인 전'으로 돌린다). 신뢰 기록 파일(Codex 설정)이 다른 이유로 바뀌어도 T 는 움직이지 않는다. 설치기가 훅 항목을 다시 쓸 때만 바뀐다.
- 설치기는 소유 기록에 그때 쓴 Codex Peek 훅 항목의 지문을 함께 남긴다(새 칸). 지금 훅 파일의 항목 지문이 기록과 다르면(누군가 다른 방법으로 바꿈) T 를 믿지 않는다 → "T 를 정할 수 없음". 지문 칸이 없는 옛 기록은 지금처럼 항목이 빠짐없이 등록돼 있을 때만(hooks-missing 판정 통과) T 로 쓴다.
- 소유 기록이 없거나 읽을 수 없거나 시각이 깨졌으면 T 를 정할 수 없다 → 지금 규칙 그대로(낮추지 않음). 관측 시각이나 파일 수정 시각으로 대신하지 않는다.
