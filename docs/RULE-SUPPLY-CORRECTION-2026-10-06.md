## 요약 (사용자용)

- **분류 담당은 말의 성격만 판단한다.** 하신 말이 ①이 프로젝트에서 계속 지킬 기준(수칙서 성격)인지 ②이미 있는 수칙을 다시 강조한 것인지 ③구현 담당의 말하기·일하는 방식에 관한 것인지 ④한 번뿐인 요청·질문·불만인지만 가른다. 어디에도 직접 쓰지 않는다.
- **수칙서로 올릴지는 구현 담당이 정한다.** 분류 결과는 다음 차례에 구현 담당에게 판단 재료로 전달되고, 구현 담당이 대화 맥락을 보고 올리거나(기존 '수칙 후보 올리기' 명령) 안 올린다(이유를 남김). 도장은 사용자가 찍는다.
- **'Claude 규칙' 칸과 결정 장부로 가는 길은 없앤다.** 규칙 칸은 사용자가 직접 쓰는 칸이고, 결정 장부는 구현 담당이 스스로 못 정하는 방향 질문만 올리는 곳이다.
- **(v12) 붙여 넣은 남의 글은 사용자 말이 아니다.** 다른 AI의 평가글을 붙여 넣으시면 그 안의 문장은 수칙 후보의 근거가 되지 못한다(LTE 수칙서 후보 4건이 전부 이 경로였음).
- **(v12) 수칙 문안은 구현 담당이 쉬운 말·주어·적용 범위를 넣어 다시 쓰고, 사용자는 그 문안에 도장을 찍는다.** 하신 말 원문은 출처 증명으로 옆에 붙는다. "고쳐서 다시 올려"라고 하시면 새 문안으로 다시 올라온다.
- **(v12) 대화에서 수칙 후보를 늘어놓거나 올릴지 묻지 않는다.** 승인·안 올림은 대시보드 한 곳에서만.
- **같은 뜻의 반복은 새 후보가 아니라 '다시 강조됨'으로 묶는다.** 예: "요구사항 낮추지 마"를 다른 말로 다시 하시면 기존 수칙 옆에 "다시 강조됨 3회"로 쌓이고, 구현 담당에게도 "사용자가 이 수칙을 다시 강조함"으로 전달된다(구현 담당이 그 수칙을 어기고 있을 가능성의 신호). 새 조건이 붙어 있으면 그 부분만 따로 다룬다.

- 사용자 말은 **수칙서 후보로만** 들어간다(CONSTRAINT-CAPTURE §0). 그 입구는 **구현 담당이 사용자 원문을 옮겨 올리는 명령**(`constraint add` — CONSTRAINT-CAPTURE §1)이다. 정리 담당 설계(CURATION 헌법)가 '구현 담당 상신=이해충돌'이라 한 것은 구현 담당이 **스스로 만든 지침**을 올리는 `rule-propose`에 대한 것이며 사용자 원문 옮기기와 구분된다(CURATION §0).
- 이 문서의 모든 부품은 위 표를 바꾸지 않는다. 설계 검증 인수조건에 "§0 정의와 충돌 없음"을 둔다.

## §1 무엇이 틀렸나 (감사 결과 — 검증 통과 2026-10-05)

1. **분류 결과의 '규칙 칸 자리'**: 분류 담당이 고른 말을 사용자가 승인하면 `c.claude`/`c.codexImplementer` 끝에 원문이 붙어 체크박스 대상이 됐다(classify.js `SEATS`의 `rule`·`approveSeatCandidate` 규칙 덧붙임). 사용자가 직접 쓰는 칸에 제안 장치의 결과가 들어간 것 — 실측: LTE 규칙 칸 2줄→6줄.
2. **분류 결과의 '결정 기록 자리'**: 같은 승인으로 `origin: user-words` 결정 행을 만든다(`DECISION_ORIGINS` 확장) — 결정 장부 출처 규칙 위반. 실데이터 오염 0건, LTE에 대기 제안 1건.
3. **구현 담당 건너뛰기**: 분류 담당의 수칙서 후보가 구현 담당 판단 없이 바로 사용자 승인 목록에 올라간다(classify.js `commitClassify` → 후보 장부 `origin: classifier`). 사용자 원문 입구(구현 담당이 옮겨 올림)와 다른 길이 생겼고, 질문·불만 문장("…해주지 않나?")이 걸러지지 않고 올라왔다.
4. **화면·안내가 그 혼합을 그대로 보임**: 수칙 카드 바로 아래 '사용자 말에서 나온 제안' 카드(규칙 칸·결정 승인 버튼) · 구현 담당 안내 '확인 대기 N건'이 규칙·결정 제안까지 합산 · 분류 지시가 `rule`·`decision` 자리를 고르게 함.
5. **같은 뜻 반복**: LTE '요구사항 낮추지 마' 계열이 승인 3·안 올림 1·새 후보 3(한 건은 '네 관문' 새 조건 포함). 분류 지시의 '같은 뜻이면 올리지 마라'는 확정 검사가 아니고, 구현 담당 상신은 정규화 원문 지문이 같을 때만 같은 후보다.

## §2 설계

### A. 분류 담당 = 성격 판단만 (쓰기 없음)
- 출력 종류 4개(자리 아님): `boundary`(수칙서 성격 — 제안 칸 지원 환경·항상 막을 것·범위 밖 + 이유) · `emphasis`(이미 있는 수칙서 항목 또는 대기 후보와 같은 뜻 — 그 항목 참조 + 새 조건이 있으면 새 조건 부분의 원문 연속 구절) · `style`(구현 담당의 말하기·일하는 방식에 관한 지속 요구) · 나머지=출력 없음(한 번뿐인 요청·질문·불만).
- 결과는 **분류 결과 장부**(`classify/<wsKey>.results.jsonl` · 덧붙이기·꼬리 보호)에만 쓴다. 후보 장부·규칙 칸·결정 장부에 쓰지 않는다.
- 원문 결속·민감 형태 생략·같은 회사 실행·3회 실패 보류·자동 계기(캠페인 마감)는 지금 그대로.
- 분류 입력의 '이미 있는 것': 수칙서(코어·서고 — 항목 번호 포함)·대기 후보·사용자가 안 올린 것. **결정 장부는 넣지 않는다**(결정 장부는 사용자 말과 무관한 저장소). 규칙 칸은 `style` 안내 중복을 막는 용도로만 넣을지 D-a에 따른다.

### B. 수칙서로 올릴지는 구현 담당이 정함
- 전달: 다음 **사람의 차례**(작업 완료 알림·하위 담당 보고 같은 비-발화 차례는 제외)에 구현 담당 주입문(매 턴 예산 안 · 지시 문장 없이 자료+명령 한 줄)에 "[사용자 말 분류 결과 — 이번 차례 판단 N건 · 대기 M건]" 블록: 이번 차례 전달분만 항목마다 id·원문 일부·종류·제안 칸·이유, 나머지는 개수만. 분류 결과는 그 말을 분류한 회사의 구현 담당에게만 전달한다(분류 실행이 구현 턴과 같은 회사인 지금 규칙 R3 유지 — Claude 쪽 결과는 Claude 구현 담당, Codex 쪽 결과는 Codex 구현 담당). 한 차례 안에서는 한 번만 싣고, 그 차례에 판단되지 않으면 다음 사람의 차례에 다시 전달한다(§4-B — 같은 글을 같은 차례에 되풀이하지 않음).
- **사람의 차례 판별(검증 2회차 보완)**: Claude 쪽은 기존 입력 단위 판별(`contract-inject` 의 `sysNotice` — 작업 완료 알림·하위 담당 보고 봉투)을 재사용한다. Codex 쪽에는 지금 **입력 단위 비-발화 판별이 없다**(`classifyPromptSource` 는 세션 출처만 봄 · `onPrompt` 는 비어 있지 않은 입력을 그대로 받음) — 이 묶음에서 Codex 입력에도 같은 봉투 판별 함수(`isSystemNotificationHook` 의 봉투 규칙)를 연결하고, Codex 고유의 비-발화 이벤트 형태는 실제 기록을 실측한 뒤에만 추가한다(추측으로 목록을 늘리지 않음). 판별 불가=사람의 차례로 보지 않는다(전달 보류 — 다음 차례에 재시도).
- 판단 명령(원문 대조는 기존 경로 재사용 · 칸 계약은 신설):
  - 올림=`constraint add --quote "<원문>" --why "…" --axis <supportedEnv|alwaysBlocker|outOfScope> [--from <결과 id>]` — 원문 대조는 지금 그대로(턴 원문 스냅샷 확인을 먼저 통과한 뒤 이번 차례 원문·직접 입력 답·최근 7일 사용자 말 순). `--from`은 분류 결과와 후보를 잇는 출처 표식일 뿐 대조를 면제하지 않는다.
  - **칸 계약(검증 1회차 blocker① — 지금 `constraintAdd`는 칸을 기록하지 않고, 칸 없는 사용자 약속 후보는 초안에서 '항상 막을 것'이 됨)**: ①구현 담당이 최종 칸을 고른다(`--axis`). `--from`이 있고 `--axis`가 없으면 분류 결과의 제안 칸을 쓴다. 둘 다 없으면(분류와 무관한 기존 상신) 종전과 같이 '항상 막을 것'. ②`constraintAdd`가 후보 첫 행에 `axis`(+분류 제안과 다르면 `axisSuggested`)를 기록한다 — 칸 이름은 닫힌 목록만(그 밖=거부). ③초안 관문(`draftEnvelopeRevision`의 사용자 약속 갈래)은 지원 환경·범위 밖을 수칙서 본문으로만 보낸다 — 이 경로가 구현 담당 상신 후보에도 그대로 적용됨을 시험으로 고정. ④**칸은 마지막 '실제 상신'이 정한다(검증 2·3회차 blocker — 후보 id 에는 칸이 들어가지 않아 같은 문장을 다른 칸으로 재상신(사용자 재요청 `--again`)해도 같은 후보다. 지금 관문·메타 회수는 그 후보의 '처음' 행을 보고, 초안 폐기 복원 행은 칸을 싣지 않으며, 채택 고아 복원은 처음 행 메타를 복사해 `proposed+axis` 행을 만든다 — 그래서 '마지막 proposed·axis 행'으로 정하면 자동 복원 행이 옛 칸을 다시 권위로 만든다)**:
    - (a) **상신 행 표식**: 실제 상신 이벤트(구현 담당 `constraint add` · 사용자 재요청 재상신 `--again` · 이 정정 전 분류 담당이 직접 쓴 옛 행)만 `submitted: true`와 상신 시각을 싣는다. 자동 상태 전이 행(초안 결속 adopted · 초안 폐기 복원 · 세대 이월 · 채택 고아 복원 · 안 올림 · 중복 정리)은 이 표식을 싣지 않는다.
    - (b) **유효 칸 단일 함수** `effectiveCandidateAxis(rows, candidateId)` = 그 후보의 `submitted` 행 가운데 **장부에 마지막으로 덧붙은 행**(덧붙이기 전용 장부의 행 순서 — 기존 후보 상태 집계가 최신 행을 정하는 방식과 같음)의 칸. 상신 시각은 표시·감사용일 뿐 순서 결정에 쓰지 않는다(몇 초의 시계 보정·같은 시각 두 상신에도 나중에 한 상신이 이김). 표식 있는 행이 하나도 없는 옛 후보(정정 전 구현 담당 상신)는 종전대로 첫 행의 칸(없으면 항상 막을 것) — 옛 자료 호환.
    - (c) **모든 소비처가 이 함수만 쓴다**: 초안 관문(`draftEnvelopeRevision` 사용자 약속 갈래)·후보 목록 집계(대시보드 상태·`codex-bridge` 후보 목록)·단건 승인 목적지(`candidateSingleDest`)·한꺼번에 올리기 계획(`candidateBatchPlan`)·확인 창 표시. 행에 실린 `axis`를 직접 읽지 않는다.
    - (d) 자동 상태 전이 행이 칸·출처를 실을 때(`ucKeepFields`)는 처음 행이 아니라 **유효 칸 함수의 값**을 싣는다(표시용 · 권위는 (b)).
    - (e) 정리 담당 후보는 `operation`으로 목적지가 정해지므로 대상 아님(사용자 약속 후보에만 적용).
    - 시험: ①같은 문장 항상 막을 것 상신→사용자 안 올림→재요청 지원 환경 재상신→초안→폐기→재작성 ⇒ 본문 지원 환경 ②같은 재상신 뒤 채택 고아 복원이 일어나도 유효 칸=지원 환경·단건 목적지=본문·한꺼번에 올리기 계획에서 서고 묶음 제외 ③옛 후보(표식 없음)=첫 행 칸 유지 ④소비처 다섯 곳이 같은 함수를 호출함(실제 실행) ⑤같은 시각의 두 상신·나중 상신의 시각이 몇 초 이른(시계 보정) 경우에도 장부상 나중 상신의 칸.
  - 안 올림=`classify skip <결과 id> --note "<이유>"`(이유 8자+ · 턴당 상신 상한에 세지 않음).
  - (v10 §3-1 채택으로 폐지 — 아래 미룸 항목은 기록용) 미룸=`classify defer <결과 id>` — 이번 차례에는 판단하지 않고 대기로 되돌림(예: 이번 차례 상신 한도를 다른 상신에 이미 써서 올릴 수 없을 때). 판단 강제(D-b)에서 '판단함'으로 친다. 올림이 상신 한도(turn-cap)로 거부되면 그 결과는 자동으로 미룸 처리된다.
- **턴당 상신 상한과 이월(검증 1회차 blocker②)**: 구현 담당 상신은 한 차례 2건까지(`CONSTRAINT_TURN_CAP`)이고 분류 결과는 한 실행 5건까지다. 그래서 한 차례에 **전달하는 분류 결과 수=그 차례의 남은 상신 수**(처음 2건)로 제한하고 나머지는 '대기'로 남겨 다음 차례에 이어 전달한다. 결과 상태=대기(미전달)·전달됨(이번 차례 판단 대상 — 턴 앵커에 목록 기록)·올림·안 올림·원문 만료. 판단하지 않은 채 차례가 끝나면(아래 관문의 유계 탈출 포함) 그 결과는 대기로 돌아가 다음 차례에 다시 전달된다(전달 횟수 기록) — 사라지지 않음. 분류 결과 자체에는 기간 만료가 없다(사용자 결정 2026-10-04 '기간 처리 없음'과 같은 태도). 단 **원문 만료와 일시 판독 불가를 나눈다(검증 2회차 보완)**: 올림은 원문 대조가 필요한데 사용자 말 원문은 보존 기간(7일) 뒤 읽을 수 없다. ①`wordExpired` 가 참일 때만 '원문 만료' — 전달하지 않고 대시보드에 그대로 보이며 판단 강제 대상 아님(조용히 사라지지 않음). ②만료 전인데 원문을 못 읽음(판독 오류·지문 불일치 — `wordText` 가 null)='읽기 보류' — 그 차례에는 전달하지 않고 대기로 두어 다음 차례에 다시 읽어 본다(복구되면 정상 전달 · 만료 시각이 지나면 ①로).
- 판단을 강제할지(D-b): 강제하면 그 차례 종료 관문이 **그 차례에 전달된 결과 중 판단 안 된 것만** 막는다 — 구조는 기존 종료 관문의 유계 반복 상한(같은 상태 3회 뒤 경보로 탈출)을 재사용하되, 판정·처분 명령은 검증 판정용(`round-judge`)이 아니라 위 두 명령이다(분류 결과 전용 상태 처리 신설). 강제하지 않으면 상태 줄·대시보드 표시만.
- 사용자에게 보이는 것: 대시보드 수칙 영역에 "사용자 말 분류 결과 — 구현 담당이 올림 n · 안 올림 n(이유) · 판단 대기 n · 다시 강조 n" 요약(읽기 전용). 승인은 기존 수칙 카드에서만(구현 담당이 올린 후보).

### C. 같은 뜻 반복 = '다시 강조됨'
- `emphasis` 결과는 강조 장부 행(`{itemRef, wordId, quote, ts}`)으로 남는다. itemRef=수칙서 항목(코어 축+번호 / 서고 번호 — 지문으로 결속, 수칙서가 바뀌면 그 세대 기준) 또는 대기 후보 id.
- 화면: 수칙 카드의 그 항목 옆에 "다시 강조됨 n회(최근 날짜)". 구현 담당 전달 블록에 "사용자가 수칙 X를 다시 강조함(n번째)" 한 줄(자료).
- 새 조건: `emphasis`에 새 조건 구절이 있으면 그 구절은 별도 `boundary` 결과로도 남겨 구현 담당이 따로 판단한다(기존 항목에 섞지 않음 — 지우지 않음).
- 검증 담당 판정 입력에는 넣지 않는다(도장 전 사용자 말 — CONSTRAINT-CAPTURE 119~124).

### D. 잘못된 길 정리
- 분류의 `rule`·`decision` 자리, `approveSeatCandidate`·`declineSeatCandidate`의 규칙 덧붙임·결정 행 생성을 없앤다.
- **결정 출처는 '새로 만들기'와 '읽기'를 나눈다(검증 1회차 blocker③ — 지금 `DECISION_ORIGINS`는 행 검사 `decisionRowValid`에도 쓰여, 그냥 빼면 과거에 정상 기록된 user-words 결정 이력이 판독에서 사라짐)**: 새 결정 행을 만드는 함수(`openDecision`·`appendDecisionRows` 신규 생성)는 `implementer`만 허용, 판독 검사는 과거 출처(`user-words`)도 계속 허용(읽기 호환). 시험: 과거 user-words open+chosen 두 행이 계속 판독됨 · 새 user-words 행 생성은 거부.
- 기존 자리 장부·결정 장부 행은 지우지도 바꾸지도 않는다(덧붙이기 전용·ab-5). 대기 중인 자리 제안(LTE 결정 대기 1건 포함)은 화면·승인 경로를 없애는 것만으로 더 이상 승인될 수 없다 — 그 프로젝트에 귀속된 하네스 대기 상태에 새 행을 덧붙이는 일은 하지 않는다(D-d 기본값). 상태 행을 덧붙여 명시적으로 닫는 쪽을 원하면 그것은 **LTE 프로젝트 폴더·수칙서 본문은 그대로지만 LTE에 귀속된 하네스 대기 상태를 바꾸는 일**이므로 대상 프로젝트·제안 목록을 보여 드리고 명시 승인 뒤에만 한다.
- 대시보드 '사용자 말에서 나온 제안' 카드의 규칙·결정 승인 부분 제거 · '분류하지 못한 사용자 말'(다시 분류·버리기)은 분류 입력 관리라 수칙 영역에 유지 · B의 요약으로 대체.
- (v12 §6-4 I로 대체 — 이 주입 줄 자체를 삭제한다 · 아래는 기록용) 확인 대기 한 줄(`pendingNoticeFor`): 사용자 도장을 기다리는 **수칙서 후보만** 센다.
- 분류 담당이 이미 낸 `origin: classifier` 대기 후보(LTE 13:16 2건 등): 수칙서 쪽 자료라 그대로 둔다(사용자가 처리).
- 문서: RULE-SUPPLY-REDESIGN §3-4·요약에 '이 문서로 대체' 표기 · DECISIONS 정정 항목.

### E. (선택) 옛 코드로 수칙서를 쓰는 일 막기 — 원인 미확정 사고 관련
- 사실: LTE 서고에 '지원 환경' 문장이 '항상 막을 것'으로 들어간 사고(2026-10-05 03:01~03:02Z)의 원인은 미확정이다. 그때 브릿지 코드는 이를 거부했어야 한다. 유력 가설=그 창의 대시보드가 설치 전에 읽은 옛 코드를 계속 사용(대시보드는 브릿지 코드를 처음 한 번 읽고 창을 다시 불러오기 전까지 그대로 씀) — 미입증.
- 대시보드에는 이미 브릿지 변경 감지·다시 불러오기 안내가 있다(extension.ts 1781 부근). 보강안: 수칙서·후보 장부에 **쓰는** 화면 동작(승인·한꺼번에 올리기·빼기) 직전에 읽어 둔 브릿지와 설치된 브릿지가 같은지 대조해 다르면 쓰지 않고 다시 불러오기를 요구. 원인 미확정이라 효과는 '가설이 맞다면'에 한정 — D-c.

### §3-1 D-b 결정안 — 쌓이는 대기 목록 없이, 분류 직후 구현 담당이 한 번 판단해 끝낸다 (채택 2026-10-07)
사용자 조건: 수칙은 ①매 턴 과다하게 쌓이지 않고 ②검증의 과다 지적을 반박하는 근거이며 ③프로젝트 전체를 관통해야 한다(선행 정본의 수칙서 정의와 같음 — REJUDGE 헌법·RULEBOOK-SIMPLIFICATION '관통 지침만'·CURATION '제안은 소수·자격은 성격'). 사용자 반문(v9): 판정이 올 때만 꺼내는 안(v7·v8)은 ⓐ사용자 말→수칙 경로를 사실상 없애고(검증이 과하게 지적해야만 수칙이 생김 — 수칙의 목적인 '과한 지적을 미리 막기'가 사후로 밀림·검증이 드문 프로젝트엔 경로 없음) ⓑ대기 기준이 무한히 쌓이면 판정마다 그 전부와 비교하는 별도 분석 단계가 된다(2건만 보이는 표시 제한은 관련성 판단이 아니라 임의 선택). 둘 다 맞아 v7·v8 §3-1(대기 기준 모음·판정 도착 자리 표시·판단 강제 없음)을 **철회**하고 아래로 바꾼다.
1. **분류 기준을 수칙 정의에 맞춤(유지)**: `boundary`는 이후 작업 전체에 계속 적용되고(지금 단계 전체에 걸친 범위 포함) 검증 담당의 판정 경계를 정하는 말만. 그 말이 어떤 지적을 범위 밖으로 돌리거나 무엇을 언제나 결함으로 만드는지 한 줄(`bounds`)을 적지 못하면 `boundary`가 아니다(하네스는 칸 존재·형식만 — 문구 목록 없음). 실측 참고: LTE 하루 분류 14회·회당 결과 0~5건(지금의 느슨한 기준·잘못된 자리 포함) — 이 기준으로 줄어드는 몫은 구현 뒤 실측.
2. **오래 쌓이는 대기 목록을 두지 않는다**: 분류는 지금처럼 캠페인 마감 때만 돈다(매 턴 아님). 그 결과는 **분류가 끝난 다음 사람의 차례에 한 번** 구현 담당에게 넘기고, 구현 담당은 **그 차례 안에서** 올림(`constraint add --from --axis`) 또는 안 올림(`classify skip --note` 이유)으로 끝낸다.
3. **판정과 비교하는 단계가 없다**: 구현 담당은 "이 말이 이후 작업 전체에 걸친 판정 경계인가"를 그 말과 대화 맥락으로만 판단한다. 반박 기능은 도장 뒤 기존 장치가 맡는다 — 승인된 수칙은 검증 담당에게 판정 경계로 전달돼 처음부터 과한 지적을 막고, 그래도 지적하면 구현 담당이 범위 밖 번호로 반박한다(판정 때 미승인 목록을 뒤질 필요 없음).
4. **올림 한도 — 전달 결과는 따로 센다(v10 · 재검증 blocker: 실행당 결과 최대 5건인데 구현 담당 상신은 차례당 2건이라 '넘김 1회'로도 5건을 다 처리 못 함)**: `CONSTRAINT_TURN_CAP`(차례당 2건)은 구현 담당이 **스스로 판단해 올리는** 상신의 남발을 막는 한도다. 그 차례에 넘겨받은 분류 결과를 `--from <그 결과 id>`로 올리는 상신은 이 한도에 세지 않는다 — 그 수는 이미 실행당 결과 상한(5건)과 `bounds` 기준으로 묶여 있다. 그래서 넘겨받은 결과는 **전부 그 차례 안에** 올림/안 올림으로 끝낼 수 있고, 넘김(`defer`)은 두지 않는다. 남용 방지: `--from`은 그 차례에 전달됐고 아직 판단되지 않은 결과 id만 받으며(그 밖=한도 계산 대상의 일반 상신으로 처리하지 않고 거부), 한 결과는 한 번만 올릴 수 있다. **결과와 문장 결속(v11 · 재검증 blocker: 전달된 결과 A의 id에 다른 사용자 문장 B를 붙이면 id 조건과 원문 대조를 모두 통과해 B가 한도 밖으로 올라가고 A는 처리된 것처럼 소비될 수 있었음)**: `--from`이 있으면 `--quote`는 **그 결과가 인용한 구절 안의 연속 구절**(같거나 더 짧게 — 최소 길이는 기존 인용 하한)이어야 한다. 아니면 거부하고 아무것도 기록하지 않는다(후보 행 없음 · 그 결과 미소비 · 자체 상신 한도 미소비). 기존 원문 대조(이번 차례 원문·직접 입력·최근 사용자 말)도 그대로 거친다. 수용 위험(3회차 검증 관찰): 인용 구절을 짧게 잘라 뜻이 뒤집히는 경우(예: '저장된 연결 설정을 지우지 마라'에서 '저장된 연결 설정을 지우'만 잘라 올림)는 형식 대조로 막지 못한다 — 이는 선행 정본(CONSTRAINT-CAPTURE: 의미 판단은 모델·형식 대조는 하네스)과 같은 경계이며, 구현 담당의 맥락 판단과 사용자 도장이 최종 관문이다(하네스에 문구 목록을 두지 않음).
5. **안 올림은 끝**: 이유가 남고 대시보드에 보인다. 사용자가 같은 뜻을 다시 말하면 분류가 '다시 강조(안 올렸던 기준)'로 표시해 다음 차례에 구현 담당에게 다시 넘긴다 — 사용자의 반복이 재검토의 계기(C의 강조 횟수와 같은 기록).
6. **판단 강제(D-b)와 종결(v10 · 재검증 blocker: 재전달 뒤에도 미판단이면 끝나는 규칙이 없었음)**: 그 차례에 넘겨받은 결과에 한해 종료 관문이 판단을 요구한다(기존 유계 상한 구조 — 같은 상태 3회 뒤 경보로 끝남). 결과마다 **전달 횟수**를 센다(전달될 때 1 증가 — 유계 탈출이든 그냥 지나침이든 같은 횟수를 씀). 미판단으로 끝난 결과는 다음 사람의 차례에 **한 번 더**(전달 2회째) 넘어간다. 2회째에도 판단되지 않으면 **종결 상태 '구현 담당 미처리'**가 된다 — 더는 전달·관문 대상이 아니고, '안 올림'으로 바꾸지 않으며(구현 담당 판단이 아니므로), 대시보드에 "구현 담당이 두 번 넘겨받고도 판단하지 않은 사용자 기준 n건"으로 사용자에게 보인다. 재개 조건: 사용자가 같은 뜻을 다시 말하면(분류가 다시 강조로 표시) 그 결과가 새 전달 주기(전달 횟수 0부터)로 다시 넘어간다 · 또는 사용자가 구현 담당에게 직접 말하면 그 말이 차례 원문이라 기존 상신 경로로 올라간다. 한 결과가 관문을 일으키는 차례는 전달 주기당 최대 2차례.
7. **원문 만료·읽기 보류**: 전달이 길어야 두 차례라 대개 해당 없음. 사용자가 7일 넘게 차례를 열지 않아 원문이 만료되면 '원문 만료'로 대시보드에만 남는다(올리려면 사용자가 기준 문장을 다시 말함 — 다시 말한 문장이 차례 원문이 되어 대조 통과 · `--from`으로 대조 면제 없음). 만료 전 판독 실패=읽기 보류(다음 차례에 다시 읽음).
8. **대시보드**: '사용자 말 분류 결과' 요약 — 올림 n · 안 올림 n(이유) · 이번 차례 판단 대기 n · 다시 강조 n · 원문 만료 n(읽기 전용). D-a `style` 안내도 같은 영역.
- B와의 관계: 이 결정안을 채택하면 B의 '전달 수=남은 상신 수·나머지 대기로 이어 전달(무한 이월)'·'미룸(defer)·상신 한도 거부=자동 미룸'은 위 4(전달 결과는 자체 상신 한도 밖·한 차례에 모두 판단·넘김 없음)로, '판단 강제는 전달분만'은 위 6(전달 2회·종결 상태)으로 대체된다. B의 칸 계약 ④(상신 행 표식·유효 칸 단일 함수)·Codex 입력 판별·원문 만료/읽기 보류 구분·C(다시 강조)는 그대로.
