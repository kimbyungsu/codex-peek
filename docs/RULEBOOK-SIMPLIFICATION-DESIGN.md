# 수칙서 소수정예 재편 설계 (RULEBOOK-SIMPLIFICATION) v4

작성 2026-08-26 · v1(blocker 7·주의 1)+v2(blocker 5)+v3(blocker 2·보완 1) 전량 반영 개정 · 상태: 설계 검증 대기
선행 조건: 서고 74→23 축소 도장(초안 대기 중)

## 헌법 (이 설계의 단일 원칙)

**수칙서는 소수정예다. 상신 자격은 성격(프로젝트를 관통하는 지침인가)이지, 이력(결함이 고쳐졌음)이 아니다.**

고쳐졌다는 것은 사건의 종결이지 지침의 탄생이 아니다. 자연히 쌓이는 것은 경험(사건·교훈)이고,
지침은 본질적으로 소수다. 경험을 지침의 통로로 흘려보낸 분류 오류가 이번 사고의 근본 원인이다.

## §0 배경 — 실측된 사고 (2026-08-26 세션, 각 항목 검증 통과 사실)

1. **서고 폭주**: 십수 항이던 수칙서가 일괄 승인 한 번에 74항 도달. 직접 원인 = resolved-blocker
   후보가 "해소된 blocker 전부"를 의미 판단 없이 자동 상신(reconcileMemoryCandidates — 필터는
   승인 지문·잠금·결속·중복·pending 12칸 등 기계 조건뿐, '관통 지침 성격' 판단 단계 부재)
   + 대기 12칸이 승인마다 뒤 후보를 순차 노출 + 사용자 일괄 승인.
2. **선별 잠금**: 74항에서 선별 합집합 상한(12항·4000바이트) 초과가 간헐 발생(작업 문맥이 넓을수록) —
   fail-closed 설계라 preview 영수증이 발급되지 않아 변경 도구 관문이 잠김. 같은 날 검증 ask도
   선별 단계에서 반복 사망(overflow·출력 형식 불량) — 검증 파이프라인 자체가 정지.
3. **표면 난잡**: 수칙서 기능 하나의 사용자 화면 어휘가 17종. 설계 참여자(사용자)조차 흐름 파악 불가
   실보고. 별개 기능 명칭 '보관함'이 수칙서 작업대의 "서고(보관함 n/max)" 표기로 재사용되는 혼용도 실측.
4. **빼기 문 부재**: 대시보드의 '빼기'는 코어(3축)에만 배선. 서고 항목을 빼는 사용자 표면이 없음
   (extension.ts:4135 — 올림=archive, 빼기=core 강제 분리). 브릿지 함수(draftEnvelopeRevision)는
   target archive 빼기를 이미 지원하므로 UI 배선 공백.

## §2 공급 판단 연결 (1차 범위 A)

### 2-1. 자동 상신 폐지와 명시 상신 신설 — 새 kind로 분리 (v1 blocker① 반영)

- **새 후보 kind `rule-manual`** 을 신설한다(기존 resolved-blocker kind 재사용 금지 — 재사용하면
  구세대 stale 정리가 "본 스캔이 새 세대에 재제안한다"는 전제로 미판단 상신을 소실시킨다).
  - 결정적 ID: envelopeCandidateId("rule-manual", wsKey|campaignId|findingId) — 세대 무관 동일.
  - 레코드 필드: candidateId·envelopeHash(상신 세대)·status·kind:"rule-manual"·origin:"manual"·
    policyVersion:2·title(결함 원문)·why·findingId·campaignId·askId·ts.
  - draftable allowlist(contract-lib.js:4247)와 대시보드 합류 조건(codex-bridge.js:3145)에
    rule-manual을 추가한다(초안 결속·adopted 전이·폐기 복원은 기존 draftable 계약 그대로 상속).
  - **세대 이월**: user-constraint carry-forward와 동형 — 구세대 proposed/미도장 adopted는 새
    세대에 정확히 1회 재발급(사용자 판단 전 소실 금지). 재스캔 의존 없음.
- **resolved-blocker kind의 신규 생성(본 스캔)을 제거**한다. 이 kind의 stale 정리(구세대
  proposed→declined)는 legacy 기록 정리 전용으로 존속(재제안 전제 주석을 정정).
- 상신 CLI: `rule-propose <findingId> --why "<왜 관통 지침인지 한 줄>"`
  - 자격(v3 blocker① 확장): 이번 캠페인에서 **닫힌 blocker — resolved 또는 demoted(강등) 닫힘**.
    resolved는 title·askId 실존(기존 결속 동일). demoted 닫힘(oos-repeat 신호의 원천)은 강등
    과정상 askId가 없을 수 있어 title 실존만 요구하고 대신 원천 oosId를 레코드에 결속한다.
  - **--why 방어(v1 주의 반영·ab-7)**: user-constraint 문안 검사와 동형 함수 재사용 —
    120자 이내·단일 행·민감정보 형태(키·토큰 패턴) 거부. 위반=상신 거부(저장 전 차단).
  - 중복: 코어·서고 기등재 정규화 문안(절단 실물 포함 양쪽) 대조 거부 — reconcile 억제 집합 재사용.
- 상신 시점 규약(절차 지침): 캠페인 마감 재판단 때 각 해소 교훈을 (a) 그 자리 한정 → 상신 안 함
  (기본값·대부분) (b) 참고 가치 → 상신 안 함(2차 경험 색인 대상·지적 장부가 이미 보존)
  (c) 관통 지침 → rule-propose. 기준: 특정 파일·버그를 넘는가 / 재발 여지 / 위반 피해.
- **장부 상신은 캠페인당 0~1건을 목표**로 한다(강제 아님·초과 시 상신은 되나 대시보드가 개수 표시).
  이 약속은 장부 kind(rule-manual·user-constraint)에 한정한다 — 합성 표시(§3-1b)는 별개.

### 2-2. why 보존 계약 (v1 blocker④ → v2 미완 재반영: 스키마 충돌 해소)

- 후보 장부: rule-manual 레코드에 why 필드(§2-1) — user-constraint의 why와 동형.
- 카드: 계산기(computeEnvelopeCandidatesFor) 합류 시 rule-manual의 why를 user-constraint와
  동일하게 전달(codex-bridge.js:3151의 kind 조건 확장).
- 승인 이력(v2 blocker② 반영): **sourceRefs는 무접촉**(현 스키마 소비자가 repoKey·contentHash·
  file·anchor를 요구 — map-provenance.js:391 — 지문형 참조를 넣으면 no-content-hash 거부).
  대신 승인 사건에 **별도 필드 `candidateRefs`** 를 신설해 `{candidateId, titleFp(sha1),
  whyFp?(sha1)}` 배열을 결속한다. **whyFp는 선택 필드다(v3 blocker② 반영)** — why를 보유하는
  kind(rule-manual·user-constraint)에서는 필수, why가 없는 legacy resolved-blocker(진행 중 초안
  보존분)는 부재가 정상이며 부재 자체가 legacy 표식이다. 수확기(registerAutoEntries)는
  candidateRefs를 소비하지 않는다(계보 기록 전용 — 수확 입력은 기존 sourceRefs 그대로).
- **승인 사건의 대상 결속(v2 blocker② 후반 반영)**: 승인 사건에 `target`("core"|"archive")과
  대상별 승인 해시(코어=새 envelopeHash·서고=새 archiveHash)를 기록한다. 수확기의 자격 대조
  (map-provenance.js:562 — 현행 코어 지문 단일 대조)는 target-aware로 확장한다: 코어 사건=
  envelopeHash 대조(기존 불변), 서고 사건=archiveHash 대조. 확장 전 기록된 legacy 사건은 기존
  대조 그대로(무회귀).

## §3 표면 단일화 (1차 범위 B) — 정상 흐름 어휘 17종 → 4종 + 표시 1

### 3-1. 사용자가 보는 것 (정상 흐름)

| 표면 | 내용 | 행동 |
|---|---|---|
| **수칙 목록** | 승인된 것 전부 한 곳(코어 3축+서고 통합 표시 — 줄마다 작은 태그 `항상`/`관련 시`) | 줄마다 [빼기] · 상단 [직접 추가] |
| **제안** | 장부 상신(rule-manual·user-constraint)만 + why 한 줄 | [승인] / [안 올림] |
| **표시 1줄** | "이번 검증에 실린 수칙 N개"(자동·관리 불가) | 없음 |

- 어휘 4종: **수칙 · 제안 · 승인 · 빼기**. 구 어휘 13종은 정상 흐름 화면·안내문에서 제거.
- '보관함' 어휘는 수칙서 화면군에서 사용 금지(별개 기능 전용 — v1 보완 반영).
- **어휘 4종 약속은 정상 흐름에 한정**한다 — 비정상 상태 복구 표면(§3-4)은 문제가 있을 때만
  나타나는 별도 문으로 존속(v1 blocker⑤ 반영).

### 3-1b. 합성 후보는 후보 계약 전체에서 분리 (v1 blocker② → v2 미완 재반영)

- oos-repeat·lineage·escalation·unused-oos는 장부 proposed가 아닌 조회 시 합성이므로
  **승인 대상이 아니라 참고 표시**로 강등한다: 제안함이 아닌 수칙 목록 하단의 접힘 줄
  ("반복 신호 N건 — 참고")로만 노출, 버튼 없음.
- **UI 버튼 제거만으로는 부족하다(v2 blocker①)** — 후보 계약 전체에서 구조적으로 분리한다:
  - 계산기 산출을 두 배열로 분리: `cands`(권위 후보 — 장부 kind인 rule-manual·user-constraint·
    legacy resolved-blocker)와 `signals`(참고 신호 — 합성 4종).
  - 참고 신호에는 과거 후보 처분 필터(declined|failed — codex-bridge.js:3154)를 적용하지 않는다
    (참고는 처분 상태가 없다 — 신호가 살아 있으면 표시, 소멸하면 사라짐).
  - 소진 보고(3167·3178)의 사용자 판단 의무·envelope-candidate mark 요구 대상에서 제외한다.
  - CLI `envelope-candidate mark`는 합성 신호 ID의 adopted|declined 기록을 **거부**한다(2679 —
    장부 개입 경로 차단). 과거에 기록된 합성 처분 행은 무시(판독 시 필터 비적용이므로 자연 무효).
- 합성 신호별 후속 경로(v3 blocker① 반영 — '유일 승격 경로' 과잉 일반화 정정):
  - escalation·lineage: 원천이 open blocker(findingId 보유) — 해소되면 resolved 자격으로
    rule-propose 가능(§2-1 기존 자격).
  - oos-repeat: 원천이 demoted 닫힘 — §2-1의 확장 자격(demoted 닫힘 허용)으로 rule-propose 가능.
  - **unused-oos: 승격 대상이 아니다** — 이 신호의 행동은 상신이 아니라 제거이므로 [빼기] 흐름의
    참고 재료로만 쓰인다(해당 수칙 줄 옆 "오래 미발동" 태그 → 사용자가 [빼기]).

### 3-2. 내부 재사용 (새 발명 금지·새 오케스트레이션 경로의 결속 명시)

- 정확한 주장: **새 권위 원시 연산은 없다**(도장 전이·WAL·양 슬롯 지문·승인 사건 그대로).
  단 [승인]·[빼기]·[직접 추가]는 그 원시 연산에 도달하는 **새 오케스트레이션 경로**이므로
  아래 대상·세대·취소·복구 결속을 각각 계약한다(v1 총평 반영 — "새 효력 경로 없음" 표현 폐기).
- **[승인]** = 초안 생성(draftEnvelopeRevision)+확인 모달+도장 전이를 한 흐름으로 연결.
  모달은 기존 계약 유지: 요약+감사용 전문 전량 표시(extension.ts:1158)·모달 뒤 초안 지문
  재확인(4192)·승인 사건과 WAL 결속(4205).
  **목적지 계약(v2 신규 blocker 반영)**: rule-manual·user-constraint 승인의 목적지는 **서고**
  (`target:"archive"` 명시 전달 — draftEnvelopeRevision의 기본값이 core라 미명시=코어 오유입
  위험, contract-lib.js:4365). 새 수칙은 "관련 시 선별"이 기본이며, 코어(전량 주입) 진입은 이
  흐름에 없다(코어 개정은 별도 명시 경로만 — 현행 유지).
- **[빼기]** = 항목 소속(코어/서고)에 따라 target 자동 분기 + 같은 흐름.
  **행 결속(v1 blocker⑥ → v2 미완 재반영·ab-2)**: 통합 목록 각 행에 `{target, targetHash
  (코어=envelopeHash·서고=archiveHash), axis, index, itemFp(정규화 문안 sha1)}` 를 실어 보낸다.
  핸들러의 클릭 시점 재검사만으로는 부족하다(v2 blocker④ — 빌더의 전이 잠금 밖 TOCTOU):
  **기대 targetHash와 removeItems 각 항목의 itemFp를 draftEnvelopeRevision 옵션으로 전달**하고,
  빌더가 **전이 잠금 안에서**(4378 잠금 획득 후) 현행 파일과 대조해 하나라도 불일치하면 거부한다
  ("목록이 갱신됐어요 — 새로고침 후 다시"). 숫자 index 단독 신뢰 금지·잠금 밖 재검사=참고일 뿐.
- **[직접 추가]** = 새 입력 권위를 만들지 않는다(v1 blocker③ 반영). 버튼은 입력창이 아니라
  안내다: "대화에 '앞으로는 ~하기로 해요'처럼 적어 주세요 — 다음 턴에 제안으로 나타납니다."
  (기존 user-constraint 자동 포착 경로 재사용 — 프롬프트 연속 구절 결속 계약 불변.)

### 3-3. 성장 억제 표시 (v1 blocker⑦ 임계 정정)

- 집계는 **코어(3축 합계)와 서고를 각각** 센다(통합 목록은 표시일 뿐 임계 단위가 아님).
- 서고 25항 초과: 목록 상단 1줄 경고("수칙이 많아지면 채점이 무뎌집니다 — 병합·정리 권장").
- 기존 30항 임계(unused-oos 재료)는 코어 3축 집계 전용으로 존속(변경 없음).
- **overflow(선별 상한 12) 정책은 불변이며, 서고 축소로 초과가 소멸한다고 주장하지 않는다** —
  모집단 축소로 발생 확률이 낮아질 뿐, 관련 수칙 13개 이상이 선택되면 여전히 중단된다(정직 한정).
  발생 시 복구 경로는 현행과 동일(빼기·병합 후 재시도) + §3-1의 [빼기] 문이 그 통로가 된다.

### 3-4. 비정상 상태 상태표 (v1 blocker⑤ 반영 — 1클릭의 숨은 전제 명시)

| 상태 | 수렴 경로 |
|---|---|

## §4 잠금(선별 fail-closed) — 이번 범위에서 변경하지 않음

- overflow=중단(절단·조용한 생략 금지)은 서고가 판정 권위를 갖는 한 유지(arc-45·46·47·59 준수).
- 권위 없는 층에서의 유연한 선별은 2차 경험 색인의 몫.

## §5 마이그레이션 (v1 blocker⑦ 범위·잠금 정정 · 순서 고정)

1. 서고 74→23 축소 도장(이미 초안 대기 — 사용자 도장 선행).
2. 공급 개정 배포: 본 스캔 제거 + rule-propose(kind rule-manual·policyVersion:2) 신설.
3. **한정 정리**: 전이 잠금 안에서 — 현 세대 proposed 중 `kind=resolved-blocker`(legacy 자동
   상신분·policyVersion 부재)만 "공급 정책 개정(v2) — 필요 시 rule-propose로 재상신" 사유로
   declined 처리. user-constraint·rule-manual은 무접촉. 처리 직전 같은 잠금 안에서 proposal
   결속(boundIds)·최신 상태를 재검사해 진행 중 초안에 묶인 후보는 건너뛴다(경합 차단).
4. 표면 교체: 새 3표면+참고 표시 활성, 구 어휘 정상 흐름 제거(§3-4 복구 표면은 존속).
5. 이후 첫 캠페인에서 마감 분류 규약(a/b/c)+rule-propose 실전 1회 확인.

## §6 비범위 (2차 이후)

- 경험 색인(무제한·색인 선별·참고 동봉·자동 은퇴 — '왜-이렇게-됐나' 계보 확장).
- 잠금 완충 재론·선별자 세션 목록 숨김(기존 보류)·C-C 모드 표면 동기.

## §7 ab 경계 자기 점검 (v1 과장 정정)

- ab-2(설정 보존): 파일 형식·계약 지문 불변 + §3-2 행 결속·클릭 시 재검사로 타 창 재승인 뒤
  오제거를 차단.
- ab-3(위조 차단): 도장 없는 효력 변경 경로 없음 — 새 경로들은 전부 기존 도장 원시 연산 경유.
- ab-4(역할 분리): 상신(나)·승인(사용자)·선별(사서)·채점(검증자).
- ab-5(기록 보존): 한정 declined는 append-only·이력 불변·rule-propose 재상신 가능.
- ab-6(멈춤): overflow 정책 불변 — 이 설계는 발생 확률을 낮출 뿐 불변식을 제공하지 않으며,
  복구 경로(빼기 문)를 정상 표면에 상설한다(과장 없는 서술).
- ab-7(유출): --why 형태 방어(§2-1)·승인 사건은 지문만(§2-2).
